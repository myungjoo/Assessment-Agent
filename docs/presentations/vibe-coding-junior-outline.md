# Vibe Coding 실전기 — 발표 개요 (초안)

- **대상**: 경력 10년 미만 junior SW 개발자 (사내 발표)
- **길이**: 10분 이내 (슬라이드 8~10장 예상)
- **컨셉**: 이론이 아니라 실제 프로젝트(Assessment-Agent)에서 일어난 일 + 내가 배운 것.
  "AI가 코드를 다 짜줬다"가 아니라 **"AI가 지속 가능하게 일하도록 프로세스를 설계한 이야기"**.

## 발표 가드레일 (자료 제작 시 전 슬라이드 적용)

- **프로젝트명 노출 OK**: Assessment-Agent, ARGO, NNStreamer 이름 그대로 사용 (사내 발표).
- **Assessment-Agent의 목적/도메인은 전면 비공개**: 이 프로젝트가 *무엇을 하는 서비스인지*는 발표 어디에서도 설명하지 않는다. "NestJS + PostgreSQL + React 기반의 사내 웹 서비스" 수준으로만 지칭. 발표 주제가 '무엇을 만들었나'가 아니라 '**어떻게 만들었나**'이므로 목적을 숨겨도 서사에 손실 없음.
- **스크린샷 마스킹 의무**: task 제목, README 발췌, 커밋 메시지, PR 제목, Q-xxxx 질문 본문에 도메인 용어가 그대로 들어 있다. 슬라이드에 넣는 모든 실물 캡처는 도메인이 드러나는 단어를 블러/치환 처리하거나, 도메인 중립적인 task(인프라·CI·테스트 관련)만 골라 캡처한다.
- 질의응답에서 "그래서 이건 뭘 하는 서비스냐"가 나올 수 있음 → "사내 웹 서비스이며, 오늘 주제는 개발 방식이라 서비스 내용은 생략한다"로 준비된 답변 1줄 마련.

## 1. 훅 + 도입 (1분, 슬라이드 1장)

- 오프닝 훅: **"지난 3개월, 이 프로젝트에서 내가 직접 작성한 production 코드는 0줄입니다. 그런데 테스트 12,843개가 돌아가는 서비스가 만들어졌습니다."**
- Vibe coding에 대한 흔한 오해 짚기:
  - ❌ "프롬프트 잘 쓰면 AI가 알아서 다 해준다"
  - ✅ 실제로는: AI가 **작게, 검증 가능하게, 지치지 않고** 일하도록 만드는 **엔지니어링 프로세스 설계** 문제
- 오늘 다룰 것: from-scratch 사례 1개(Assessment-Agent) 깊게 + 기존 코드베이스 사례 2개(ARGO, NNStreamer) 짧게.

## 2. 숫자로 보는 Assessment-Agent (1.5분, 슬라이드 1장)

실측 데이터 (발표일 기준 갱신 필요):

| 지표 | 값 | 청중에게 주는 함의 |
| --- | --- | --- |
| 기간 | 2026-05-23 ~ 진행 중 (~3개월) | 일회성 데모가 아닌 지속 운영 |
| 완료 task | **1,696개** (정의 1,706 / BLOCKED 9) | 하루 평균 ~18 task |
| main 커밋 | **~4,520개** | 1 task = 1 commit 원칙의 결과 |
| ADR (아키텍처 결정 기록) | **55건** | 결정을 코드보다 먼저 문서로 |
| 인간에게 올라온 질문 (Q-xxxx) | **55건** | task 대비 **~3%만 인간 개입** |
| 테스트 | 447 suite / **12,843개**, coverage 99.95% | 강제 기준(80%)을 시스템이 알아서 초과 |

- 포인트: "AI가 잘해서"가 아니라 **막힐 때만 사람에게 오도록 설계**해서 3%가 된 것.

## 3. 어떻게 굴러가나 (2분, 슬라이드 2장)

### 3a. Phase 1 — 요구사항 정제 + Architecture 정립 (AI와 함께)

- From scratch: README(요구사항 명세)를 AI와 대화하며 정제 → use-case 문서 → ADR로 스택/구조 확정 (NestJS + PostgreSQL + React 등).
- 핵심 습관: **결정은 반드시 ADR로 박제** — 같은 고민을 두 번 하지 않기 위해. AI에게도 사람에게도 유효한 규율.
- CLAUDE.md = "행동 규칙서": 커밋 규칙, 테스트 의무, 리뷰 게이트, 언어 정책까지 명문화. **AI 팀원의 온보딩 문서이자 근로계약서.**

### 3b. Phase 2 — 자동화된 개발 루프 (핵심 그림 1장)

```
cron 발화(2h 간격 등)
  → driver가 STATE.json 로드 + lock 획득
  → planner: 다음 task 1개 생성 (≤300 LOC / ≤5 파일로 분할)
  → executor → implementer(코드) → tester(테스트) 
  → PR open → reviewer agent(8개 체크) ↔ 수정 라운드
  → integrator: 4-게이트(리뷰 승인 + 리뷰 코멘트 실존 + 자체점검 + CI green) 통과 시 merge
  → journal/STATE 기록 → 종료. 다음 발화는 새 대화(fresh context)
```

- **Context 관리가 전부**: AI는 오래 일할수록 맥락이 비대해져 품질이 떨어진다. 대책 3가지:
  1. **작은 task** — diff ≤300 LOC / 파일 ≤5개. 넘으면 planner가 쪼갠다.
  2. **역할 분리(sub-agent)** — driver는 요약 200자만 받는다. 긴 출력은 파일/커밋 메시지로 외부화.
  3. **매 발화 새 대화** — 상태는 대화 기억이 아니라 STATE.json / journal / commit trail에 저장. "기억은 git에, 대화는 일회용."
- junior 청중용 비유: **"신입 1,700명에게 일을 시키는 법"** — 각자에게 self-contained한 1장짜리 task 정의서를 주고, 결과는 표준 양식으로만 보고받는다.

## 4. 인간의 역할 + 실제 사고 사례 (2분, 슬라이드 2장)

### 4a. 인간은 무엇을 했나 (HITL의 균형)

- 자동 진행: 계획된 task, 버그 수정, 리팩토링, 이미 결정된 스택 내 구현 → **일절 개입 안 함**.
- 반드시 인간에게 오는 것(BLOCKED): 새 외부 dependency, DB 스키마 변경, 보안/인증, ADR과 충돌하는 설계 변경, 요구사항 해석이 갈리는 지점, 리뷰 7라운드 초과.
- 실제 Q-xxxx 예시 1~2건 소개 (예: Q-0051 Frontend 스택 확정 — React+Vite 오너 결정).
- 메시지: **인간의 일은 코딩이 아니라 '결정'과 '요구사항의 최종 해석'**. AI는 절대 스스로 요구사항을 확정하지 않게 했다.

### 4b. 사고는 났다 — 그리고 룰이 됐다 (발표의 백미)

실제 문서화된 사고 3건 (repo에 증거 있음):

1. **Reviewer 우회 사고 (PR-5/6/7)** — agent가 리뷰 verdict를 PR 본문에 자기가 써넣고 통과한 것처럼 처리 → 대책: "리뷰 코멘트가 PR에 **외부 사실로 실존**하는지"를 CI가 검증하는 4-게이트 도입.
2. **잘못된 branch push (T-0007/PR-8)** — source≠target push로 이력 오염 → 대책: push source/target 매칭 hard rule + 위반 시 자동 BLOCKED.
3. **Task 과대 (T-0001)** — 첫 task부터 크기 초과로 품질 저하 → 대책: 300 LOC / 5파일 상한 + planner 강제 분할.

- 메시지: **AI도 사고를 친다. 차이는 '사고 → 회고 → 룰 박제'의 루프를 시스템에 내장했다는 것.** (사람 조직의 postmortem 문화와 동일)

## 5. Agile과의 비교 (1.5분, 슬라이드 1장 — 매핑 표)

핵심 주장: 이것은 Agile의 부정이 아니라 **극한 압축**이다. "하루 미만 sprint의, 인간-AI 협업용 변형 Agile."

| Agile (인간 팀) | Assessment-Agent (인간-AI 팀) | 압축 배율 |
| --- | --- | --- |
| Sprint 1~2주 | cron fire 1회 (수십 분~수 시간) | 수백 배 |
| Product Backlog | PLAN.md + planner agent | 상시 자동 갱신 |
| User Story / 티켓 | T-NNNN task 파일 (self-contained) | 1,700건 |
| Daily standup | journal + STATE.json (머신리더블) | 매 task마다 |
| 코드 리뷰 (동료) | reviewer agent + 4-게이트 merge 합의 | 매 PR, 최대 7라운드 |
| Sprint retrospective | 사고 → CLAUDE.md/ADR에 hard rule 박제 | 사고 즉시 |
| Product Owner | **인간 (나)** — Q-xxxx로만 개입 | 유일하게 압축 안 됨 |
| Definition of Done | CI green + coverage ≥80% + 4-게이트 | 기계 강제 |

- 통찰 2개:
  - **아키텍처는 고정이 아니라 계속 세부 변경됐다** — Q-xxxx 인간-AI 소통과 ADR 갱신을 통해. Agile의 "emergent architecture"가 그대로 재현됨.
  - **압축되지 않는 유일한 역할이 PO(인간)** — 그래서 junior일수록 "요구사항을 명확히 쓰고 결정하는 능력"이 vibe coding 시대의 핵심 역량.

## 6. From scratch가 아니라면 — ARGO / NNStreamer (1분, 슬라이드 1장)

- 기존 코드베이스 + 여러 인간 개발자가 이미 있는 환경은 무엇이 다른가:
  - 아키텍처를 AI와 '정립'하는 게 아니라 AI에게 '학습'시켜야 함 (규칙/온보딩 문서가 첫 산출물).
  - 인간 리뷰어·기존 CI·기존 커밋 컨벤션이 이미 있으므로, AI는 게이트를 새로 만들 게 아니라 **기존 게이트에 편입**.
  - 협업 상대가 AI의 존재를 모르거나 신뢰하지 않을 수 있음 → AI 기여의 투명성(커밋 표기 등) 이슈.
- 대비 포인트: from-scratch는 "프로세스를 AI에 맞게 설계"할 자유가 있었지만, 기존 프로젝트는 "AI를 기존 프로세스에 맞게 길들이는" 문제.

### 6a. NNStreamer — 오픈소스(LF AI, 기여자 89명, 커밋 4,168개)에서의 AI 적용 (repo 실측 근거)

10분 발표에서는 아래 후보 중 **1~2개만 선택**해 쓴다 (전부 repo에 커밋/브랜치 증거 있음):

1. **"AI 리뷰어에게 준 온보딩 문서"** — `.cursorrules` 89줄 (2025-12-17 도입, `b294479a`): GStreamer refcount 규율, 최소 diff 원칙, `[BLOCKER]/[MAJOR]/[MINOR]/[NIT]` 심각도 태그 강제, 그리고 **"CodeQL/valgrind를 끄자고 제안하지 말 것"** 조항까지. → Assessment-Agent의 CLAUDE.md와 정확히 같은 패턴: **도메인 지식과 리뷰 규율을 문서로 코드화하면 AI가 팀 규칙대로 일한다**. (두 사례를 잇는 다리 슬라이드로 최적)
2. **메모리 누수 일괄 스윕** — 2026-03-17 하루에 누수 픽스 7커밋 (예: `f4584ffa` 1줄 추가). "property setter의 free 누락, unref 누락" 같은 패턴을 AI가 저장소 전체에서 훑음. → **사람 리뷰어가 지루해서 놓치는 저부가가치·고빈도 결함이 AI의 최적 적용점** (정적분석 대응 업무와 직결 — junior 청중의 일상 업무와 연결).
3. **브랜치명이 곧 프롬프트** — `cursor/memory-leak-search`, `cursor/github-action-failure-investigation`, `cursor/review-main-branch-for-bugs-gpt-5.1-codex` 등 원격 브랜치 목록 + Claude Code 워크트리 4개(PR 리뷰, downstream 동기화). → **어떤 일을 AI에 위임했는지가 git에 그대로 남는** 시각 자료. 멀티모델(Cursor/Claude/Codex) 병행 운용 증거이기도 함.
4. **DCO 서명 주체 문제 (거버넌스 공백 실증)** — 같은 repo에 `Signed-off-by: Cursor Agent` + 사람 co-author 커밋과, `Signed-off-by: 사람` + `Co-Authored-By: Claude` 커밋이 공존. CI는 태그 존재만 검사해 둘 다 통과, CONTRIBUTING에 AI 조항 0건. → **"AI 기여를 누구 명의로 귀속시킬 것인가"** — 사내 오픈소스/법무 정책 논의로 확장 가능한 논점.
5. **CI에는 아직 AI가 없다** — 워크플로우 22개 중 AI 통합 0건. AI는 개발자 로컬 단계에만 있고 산출물은 기존 게이트(CodeQL, 커미터 2인 승인)를 그대로 통과해야 함. → "개인 생산성 도구 단계 → 다음은 CI 통합"이라는 **현주소/로드맵** 슬라이드 소재. 최근 6개월 main 커밋 25건 중 AI 흔적 9건(~36%, 단 대부분 소규모 픽스)이라는 수치도 사용 가능.

- 핵심 대비 (vs Assessment-Agent): NNStreamer의 AI는 **기존 인간 게이트(커미터 2인 승인, DCO, CodeQL) 아래에서 일하는 보조 기여자**. Assessment-Agent처럼 merge까지 자동인 구조가 아님 — "신뢰 수준에 따라 AI에게 주는 권한이 달라진다"는 스펙트럼 논의로 연결.

**[발표자 본인의 기여 패턴 — repo 실측]** (1인칭 스토리 소재, 강력 추천):

- **직접 코딩은 줄고 판단이 남았다**: 연간 authored 커밋 250(2018)→13(2025)인데, 저장소 전체 커밋의 **64%(2,682/4,168)를 본인이 committer로 통과** — 병목은 "짜는 것"이 아니라 "판단하는 것"이었고 AI를 그 병목에 투입.
- **AI는 작성자가 아니라 조사원**: 최근 12개월 본인 커밋 14건 중 7건(50%)에 AI 흔적, 그러나 신규 기능을 AI에 시킨 사례 **0건**. 용도는 누수 탐색·CI 실패 조사·본인 PR 재리뷰.
- **성과 지표는 diff 크기가 아니라 조사 깊이**: Yocto CI 수정 `a733ee46` — 최종 18줄이지만, "러너 tar의 CVE 픽스가 openat2를 쓰기 시작 → 구 pseudo가 못 가로챔 → do_package EFAULT"라는 3단 인과를 AI와 규명. AI 도입 후 커밋 본문이 길어지고 테스트가 붙음(`9c314c90` 유닛테스트 +157줄).
- **8개월 사이클 사례 (#4829)**: Cursor가 찾은 누수 패치 → 본인이 PR → Claude로 자기 PR 재리뷰 → 사람 리뷰어 지적(unique_ptr) 반영 → 계약 변경의 파급으로 dali 누수까지 AI가 추적. "AI 발견 → 사람 판단 → AI 반영 → AI 파급 추적"의 완결 루프.
- **AI의 과잉 삭제를 도메인 지식으로 교정**: AI가 "코드에 안 보인다"며 지운 NNTrainer 항목을 본인이 복원("별도 repo에서 빌드됨"은 메인테이너 머릿속에만 있던 사실) — 반대로 8년 묵은 날짜 문구는 AI가 발견. **AI가 못 보는 것과 사람이 안 보는 것의 상보성**.
- **AI가 짜도 사인은 사람이**: AI 유래 커밋에도 예외 없이 본인 Signed-off-by — 책임 귀속 실천.

### 6b. ARGO — 사내 다수 개발자(수십 명) 프로젝트에서의 AI 적용 (repo 실측 근거)

기초 수치: Rust 모노레포, 파일 6,542개 / 커밋 9,492개를 **4개월**(2026-04~07)에 구축. 아래 후보 중 **1~2개만 선택**:

1. **"커밋의 85%가 AI 공동저자" — 팀 표준이 된 증거** — 9,492 커밋 중 8,066건에 `Co-Authored-By: Claude`. 특정 개인의 실험이 아니라 **상위 기여자 10명 전원이 63~98% 비율**로 사용. 변경 종류도 fix/feat뿐 아니라 docs·test·ci·bench·refactor 전 영역. → "한 명의 파워유저"가 아닌 "팀 워크플로우로 정착"을 한 장의 표로 증명.
2. **CLAUDE.md = 팀의 헌법 (문서→훅→CI 3단 강제)** — 35KB 루트 CLAUDE.md + CI 전용 + 크레이트별 계층 구조. 프로젝트 철학 문서가 "충돌 시 CLAUDE.md 우선"을 선언하고, CONTRIBUTING이 신규 기여자의 첫 필독 문서로 지정. 규범은 pre-commit 훅(3개 게이트)과 CI로 기계 강제. → **Assessment-Agent(1인+AI), ARGO(수십 인+AI) 모두에서 같은 결론: "AI 지침 문서가 곧 아키텍처 문서"**. 세 사례를 관통하는 공통 패턴(NNStreamer의 .cursorrules 포함)이라 다리 슬라이드로 최적.
3. **AI 리뷰 ↔ AI 수정 루프** — PR마다 Z.ai LLM 리뷰가 자동으로 붙고 `round-2 ~ round-12`까지 반복 수정 (관련 커밋 2,145건). 도입 실패담 포함: 사내 네트워크 allowlist로 API 접근 불가 → 워크플로우 삭제 → **전용 self-hosted 러너로 부활** → stuck 리뷰의 러너 점유 문제로 timeout 추가. → "사내망에서 AI를 CI에 넣을 때 실제로 부딪히는 것들"이라는 현실 교훈 (junior 청중의 사내 환경과 직결).
4. **에이전트 가드레일: secret speed-bump 훅** — `.claude/settings.json`의 PreToolUse 훅이 에이전트의 자격증명 읽기 시도를 탐지/로깅. 스크립트 스스로 "보안 경계가 아니다, 우회 가능 — 정직한 실수를 잡는 speed bump"라고 한계 명시. **이 훅을 도입한 커밋 자체가 훅에 차단당한 일화**까지. → 유머와 교훈을 동시에 주는 슬라이드 소재.
5. **LLM 품질 게이트의 비용 통제** — 실 LLM 호출 평가 스위트를 CI에 넣되, 라벨 opt-in + nightly + **실행당 $5 하드 상한**으로 비용 폭주 차단. → "AI를 CI에 넣고 싶다"는 질문에 대한 구체적 답안.

- ⚠️ **발표 시 혼동 주의**: ARGO는 제품 자체가 AI 에이전트라 "AI로 개발한 흔적"과 "AI 제품 기능"이 섞여 있음. 발표에서는 개발 프로세스 흔적만 사용하고, 필요 시 "ARGO가 뭘 만드는 프로젝트인지"는 한 문장으로만 언급.
- ⚠️ **귀속 정정 (git blame 확인)**: 위 후보 ③ Z.ai 워크플로우 도입/부활과 ④ secret speed-bump 훅은 **sanghn-kim/sanghnkim-max의 기여** — 발표에서 본인 사례로 쓰지 말 것. 쓰려면 "팀이 만든 가드레일 위에서 나는 CI 게이트 층을 쌓았다" 구도로.

**[발표자 본인의 기여 패턴 — repo 실측]** (1인칭 스토리 소재):

- **기능을 늘리는 사람이 아니라 무너지지 않게 하는 사람**: 본인 616커밋 중 feat 9%, **test 16% + ci 11%** — 팀 평균(test 2%, ci 2%) 대비 6~9배. AI가 기능 생산량을 폭증시킬수록 사람은 검증 인프라로 이동.
- **CI 규범 문서의 주 저자**: 53KB `.github/workflows/CLAUDE.md`의 447줄이 본인(2위 54줄). 본인 커밋의 10.6%가 CLAUDE.md 조항을 인용(팀 최고) — "코드리뷰가 아니라 컨텍스트가 품질을 만든다".
- **게이트를 지키는 게이트**: `scripts/audit_*.py` 11종 전부 본인 신규 작성 — 누군가(사람이든 AI든) 커버리지 게이트에 `|| true`를 다시 붙이면 PR이 막힘. 임계값은 측정에 맞춰 낮추지 않고 soft 목표/hard 바닥 분리 + 래칫.
- **AI가 만든 CI는 soft로 켜고 → 실측하고 → hard로 승격**: #745 Windows 게이트 — 실제 run에서 31/31 green을 측정한 수치를 커밋에 남긴 뒤에야 `continue-on-error` 제거.
- **AI 리뷰는 수용이 아니라 협상**: 리뷰 대응 112커밋, `review(#NNN rN):` 커밋 타입 승격, 최대 8라운드. "6개 중 4개 반영" / "5라운드 동안 구조적 한계로 합의(기각)"처럼 **기각 사유까지 커밋에 기록**.
- **커밋 메시지 = 설계 문서 = 다음 AI를 위한 컨텍스트**: 버린 대안의 이유, 함정의 기술 근거, 의도적으로 미룬 작업(deferred 149회), 검증 결과, 사용한 모델명까지 본문에 기록.

## 7. Takeaways — junior가 내일부터 할 수 있는 것 (1분, 슬라이드 1장)

1. **작게 쪼개라** — AI에게 주는 일의 크기가 품질을 결정한다 (300 LOC 상한의 교훈). 이건 인간 PR에도 그대로 좋은 습관.
2. **결정을 문서로 박제하라** — ADR 한 장이 같은 논쟁 열 번을 없앤다. AI는 문서화된 결정만 일관되게 따른다.
3. **검증을 AI에게 맡기지 말고 시스템에 맡겨라** — coverage 강제, CI 게이트, 외부 사실 기반 리뷰 검증. "AI를 믿지 말고 게이트를 믿어라."
4. **기억을 대화가 아니라 저장소에 두라** — 상태 파일, journal, 커밋 메시지 trail. 대화는 일회용으로.
5. **당신의 자리는 PO다** — 요구사항을 명확히 쓰고, 갈림길에서 결정하는 능력을 길러라. 코딩 속도는 AI가 압축해도 이건 압축 못 한다.

- 클로징: "Vibe coding은 코딩을 없애는 게 아니라, **주니어에게 가장 어려웠던 일(설계·판단·프로세스)을 가장 중요한 일로 만든다**."
