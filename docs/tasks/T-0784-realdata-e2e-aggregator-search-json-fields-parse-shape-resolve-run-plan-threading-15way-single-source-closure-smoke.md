# T-0784 — realdata-e2e step④ aggregator search-json-fields↔parse-shape 합류 15-way single-source closure non-gated build-time smoke 신설

## Why

PLAN.md §109(🟢 실 평가 e2e, P5)의 build-time 순수 layer 는 최외곽 단일 진입 `buildRealDataE2eRunPlan(seeds, modelId, run)` → `{pipeline, run}`(T-0597)을 산출하고, 그 검증된 `runPlan` 을 pre-실행 aggregator `buildRealDataE2eStepArgs(runPlan, activities, results)` → `{evaluation, publish}`(T-0601)에 통째로 넘긴다. 직전 sweep(T-0778~0783)은 aggregator 산출의 **evaluation-leg(inputs·callArgs·modelId)** + **publish-leg(report·commandArgs·searchArgv·resolve-argv)** + **collect-leg(collectCallArgs)** 세 leg 의 표면을 단일 source 로 묶어 14-way 를 완성했다.

그러나 step④ 결과 박제 chain 의 search seam 에는 14-way 가 닫지 않은 **요청-필드↔추출-shape set-equality seam** 이 남아있다 — aggregator 가 산출한 `stepArgs.publish.searchArgv` 의 `--json` 요청-필드 토큰(`searchArgv[6] === "number,title,body"`, T-0782 13-way 는 이를 **positional 리터럴 string** 으로만 단언, `expect(searchArgv[6]).toBe(REAL_DATA_RESULT_ISSUE_SEARCH_JSON_FIELDS)` 376행)이, 그 다음 단계 search-parse(`parseRealDataResultIssueSearchOutput`, T-0587)가 `searchStdout` 으로부터 추출하는 `RealDataResultIssueSearchHit` shape 키 집합(`REAL_DATA_RESULT_ISSUE_SEARCH_PARSE_SHAPE_KEYS = ["number","title","body"]`)과 **set-equal**(콤마 split 집합 == 추출 shape 키 집합 == 실 파싱 hit 의 `Object.keys` 집합)임은 aggregator+resolve 종단 closure 에 미합류다.

search-json-fields↔parse-shape 축은 14-way 가 잡은 14축과 distinct 한 표면이다:

- **search-json-fields ↔ parse-shape set-equality 축(본 task 의 새 표면)** — aggregator 가 산출한 `searchArgv[6]`(`--json` 요청-필드 문자열)을 콤마로 split·trim 한 집합이:
  - `REAL_DATA_RESULT_ISSUE_SEARCH_PARSE_SHAPE_KEYS`(`["number","title","body"]`, search-json-fields helper 70~74행 export)와 set-equal(요청한 필드 == 추출 shape 가 정규화하는 키).
  - AND `searchStdout` 으로부터 실제 파싱된 각 `RealDataResultIssueSearchHit` 의 `Object.keys` 집합과 set-equal(요청한 필드 == 실 파싱 산물의 키 — gh 응답에 추가 필드 섞여도 `{number,title,body}` 만 정규화).
  - 이 set-equality 가 aggregator 가 evaluate/publish 로 thread 하는 **그 동일 `runPlan` 의 publish-leg searchArgv** 에서 나온다. 즉 aggregator 가 요청한 `--json` 필드와 search-parse 가 추출하는 shape 가 단일 검증 source 에서 어긋남 0 — 그 parse-shape 의 `number` 가 resolve action `issueNumber` → argv[2] → post 로 thread 됨이 search→parse→resolve→post 종단 closure 에 미합류.

직전 sibling 들은 이 set-equality 축을 aggregator convergence closure 에 합류시키지 않았다:
- **T-0783 (aggregator 14-way)**: collect-leg collectCallArgs 재유도 + collect/evaluate modelId 공유 + search-argv 전체-벡터 위치-정합 + resolve-argv + command-args + descriptor + summary + inputs + modelId + marker + resolve + post 를 묶었으나, searchArgv 의 `--json` 토큰은 **deep-equal 의 한 원소(positional 리터럴 string)** 로만 등장 — **그 토큰을 set 으로 split 한 집합이 PARSE_SHAPE_KEYS 집합·실 파싱 hit 키 집합과 set-equal 임은 미합류**.
- **T-0782 (aggregator 13-way)**: `expect(searchArgv[6]).toBe(REAL_DATA_RESULT_ISSUE_SEARCH_JSON_FIELDS)`(376행) 으로 `--json` 토큰의 **리터럴 string 동일성** 만 단언 — split 후 set-equal·실 파싱 hit 키 정합 0.
- **T-0775~0781 (aggregator 4~12-way)**: 전부 search-argv positional / resolve / descriptor / inputs / collect 축만 잡음 — `--json` 요청-필드와 parse-shape 의 set-equal 합류 0.
- **search-json-fields self-guard**: `assertRealDataResultIssueSearchJsonFieldsMatchParseShape`(T-0657, search-json-fields helper 188행) + search-argv 빌더 내부 self-wire(135~148행)가 `REAL_DATA_RESULT_ISSUE_SEARCH_JSON_FIELDS` ↔ `REAL_DATA_RESULT_ISSUE_SEARCH_PARSE_SHAPE_KEYS` round-trip 을 박제했으나 **aggregator(`buildRealDataE2eStepArgs`) 진입·실 search-parse·resolve·post 미합류**(빌더 단독 self-guard — 합성 stepArgs.publish.searchArgv 에서 추출한 토큰 ↔ 실 파싱 hit 키 의 종단 정합 0).
- **search-parse spec**: `parseRealDataResultIssueSearchOutput` 단독 spec 이 `{number,title,body}` 정규화를 박제했으나 **aggregator 가 요청한 searchArgv `--json` 필드와의 set-equal 합류 0**(파서 단독, argv-요청-측 미연결).

본 task 는 그 빈 자리를 채워 **aggregator 가 산출한 searchArgv 의 `--json` 요청-필드(searchArgv[6])가, 그 다음 단계 search-parse 가 실제 추출하는 hit shape 키와 set-equal 임을, 그리고 그 parse-shape 의 number 가 resolve→post 로 thread 됨을 collect-leg·evaluate-leg·publish-leg 와 묶어 closure 에 합류**시킨다. 단일 source `(seeds, modelId, run, activities, results, search-stdout, exec-stdout)` 로부터:

1. **search-json-fields ↔ parse-shape set-equality(축 15, 본 task 의 새 표면)** — `runPlan = buildRealDataE2eRunPlan(seeds, modelId, run)` → `stepArgs = buildRealDataE2eStepArgs(runPlan, activities, results)` → `stepArgs.publish.searchArgv[6]`(`--json` 토큰)을 `,` split·trim 한 `Set` 이 (a) `new Set(REAL_DATA_RESULT_ISSUE_SEARCH_PARSE_SHAPE_KEYS)`(`["number","title","body"]`) 와 set-equal, AND (b) `searchStdout` 으로부터 `parseRealDataResultIssueSearchOutput(searchStdout)` 가 파싱한 각 hit 의 `Object.keys(hit)` 집합과 set-equal. 즉 aggregator 가 요청한 필드 == 추출 shape == 실 파싱 산물 키 가 단일 source 에서 set-equal.
2. **parse-shape number → resolve action issueNumber → post thread(축 15 묶음)** — 실 파싱 hit 의 `number`(N) 가 `resolveRealDataResultIssueGhCommandPlan(searchStdout, commandArgs).action.update.issueNumber === N` AND `argv[2] === String(N)` AND `outcomeReport = buildRealDataResultOutcomeStepArgs(runPlan, execStdout)` 의 `issueNumber === N` — 요청한 `number` 필드가 추출→resolve→post 로 정확히 thread.
3. **collect-leg call-args 재유도(축 14, 14-way 묶음 항)** — `runPlan.pipeline.collectCallArgs` 가 byte-identical deep-equal `buildRealDataCollectCallArgs(seeds)`.
4. **collect/evaluate modelId 공유(축 14, 묶음 항)** — `runPlan.pipeline.modelId === modelId === stepArgs.evaluation.callArgs[i].options.modelId`.
5. **search-argv 전체-벡터 위치-정합(축 13, 묶음 항)** — `stepArgs.publish.searchArgv` byte-identical deep-equal `["search","issues","--match","body",commandArgs.searchQuery,"--json","number,title,body","--limit","30"]`.
6. **resolve-argv update/create 위치-정합(축 12, 묶음 항)** — hit N → `["issue","edit",String(N),"--title",updateArgs.title,"--body",updateArgs.body]`, hit 0 → `["issue","create",...createArgs,...labels]`.
7. **publish-leg command-args-labels + title/body 두 경로 + descriptor·summary 재유도(축 6~11)** — `createArgs.labels` deep-equal `["realdata-e2e","result"]`, `{title,body}` == `descriptor.{title,body}`, summary 재유도.
8. **evaluation-leg inputs 재유도 + 페어링(축 4~5)** — `inputs == buildRealDataEvaluationInputs(activities)`, `callArgs[i].input === inputs[i]`.
9. **marker 3-축 + resolve issueNumber + post run-identity(축 1~3, 종단)** — `descriptor.marker === commandArgs.searchQuery === searchArgv[4]`, resolve issueNumber → post run token 전파.

이 15-way(search-json-fields↔parse-shape set-equal + parse-shape number thread + collect-leg 재유도 + collect/evaluate modelId 공유 + search-argv 전체-벡터 위치-정합 + resolve-argv 위치-정합 + command-args labels 고정상수 + command-args title/body 두 경로 + descriptor.{title,body} 재유도 + summary + inputs + marker 3-축 + resolve issueNumber + post run-identity)가 **검증 source `(seeds, modelId, run, activities, results)`** single-source 로 수렴함이 **search-or-update 멱등성**(REQ-009)·**raw 미보유 평가 입력/결과 집계 정합**(REQ-032)·**결과 리포트 재실행 정합**(REQ-037)의 aggregator-level "aggregator 가 search 로 요청한 `--json` 필드 == 그 다음 단계 parse 가 추출하는 hit shape == 실 파싱 산물 키, 그 number 가 resolve→post 로 어긋남 0 thread" 의 종단 닫음이다. **e2e 의 search 요청-측(argv)과 응답-파싱-측(hit shape) 이 단일 검증 source 에서 set-equal 로 맞물리는 seam slice** 다.

gap 확인(git grep, origin/main 0cea7ade): aggregator-* sweep smoke 14파일(4~14-way) 중 `--json` 토큰 split 집합 == `PARSE_SHAPE_KEYS` 집합 == 실 파싱 hit 키 집합 의 set-equal 단언 0(13-way 는 376행 positional 리터럴 string `toBe` 만). `aggregator-*search-json-fields* / *parse-shape* smoke 파일 부재` + `git log origin/main` 동일 영역 박제 commit 0.
