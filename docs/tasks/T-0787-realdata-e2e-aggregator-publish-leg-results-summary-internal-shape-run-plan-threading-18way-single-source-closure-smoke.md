# T-0787 — realdata-e2e step④ aggregator publish-leg report.summary 내부-shape per-result 1:1 집계 thread 합류 18-way single-source closure non-gated build-time smoke 신설

## Why

PLAN.md §109(🟢 실 평가 e2e, P5)의 build-time 순수 layer 는 최외곽 단일 진입 `buildRealDataE2eRunPlan(seeds, modelId, run)` → `{pipeline, run}`(T-0597)을 산출하고, 그 `runPlan` 을 pre-실행 aggregator `buildRealDataE2eStepArgs(runPlan, activities, results)` → `{evaluation, publish}`(T-0601)에 통째로 넘긴다. 직전 sweep(T-0778~0786)은 aggregator 산출의 evaluation-leg + publish-leg 표면 + collect-leg 내부-shape(serviceIdentities 배열 깊이, T-0785) + evaluation-leg 내부-shape(input 필드 깊이, T-0786)를 단일 source 로 묶어 17-way 를 완성했다. 특히 publish-leg 의 summary 축은 T-0776(aggregator 7-way) 이 `stepArgs.publish.report.summary == buildRealDataResultIssueCommandPlan(results, runPlan.run).report.summary` **top-level deep-equal** + 특정 3-result fixture 의 고정-리터럴 슬롯값(`byDifficulty.easy===1` 등)으로 합류시켰다.

그러나 publish-leg 의 **summary 내부-shape 깊이**(EvaluationResult[] → RealDataResultSummary 집계 차원)에는 17-way 가 닫지 않은 seam 이 남아있다 — aggregator 가 산출한 `stepArgs.publish.report.summary`(type `RealDataResultSummary`)의 각 집계 필드(`count`·`byDifficulty`(3 슬롯)·`byContribution`(4 슬롯)·`totalVolume`)가, 검증 source `results[]`(type `EvaluationResult[]`)로부터 **원소별 1:1 집계 불변식**(각 `results[i]` 가 자기 `byDifficulty[results[i].difficulty]` 슬롯 +1·`byContribution[results[i].contribution]` 슬롯 +1·`count` +1·`volume` 누적, 그리고 **전 enum 슬롯 존재**(`DIFFICULTIES` 3 + `CONTRIBUTION_LEVELS` 4, 미등장 슬롯도 키 존재·값 0))으로 production 집계 위임 `buildRealDataResultSummary(results)` 와 byte-identical 임은 aggregator+resolve 종단 closure 에 미합류다.

publish-leg summary 내부-shape 축은 17-way 가 잡은 17축과 distinct 한 표면이다:

- **publish-leg summary 내부-shape per-result 1:1 집계 thread 축(본 task 의 새 표면)** — aggregator 가 `buildRealDataE2eStepArgs` 위임 `buildRealDataResultPublishStepArgs`(T-0598 류) 경유 `buildRealDataResultIssueCommandPlan(results, run)`(T-0594) → `buildRealDataResultReportPlan`(T-0593) → `buildRealDataResultSummary(results)`(T-0580) 로 산출한 `stepArgs.publish.report.summary` 가:
  - `buildRealDataResultSummary(results)`(production 집계 위임) 와 **필드별 byte-identical**(`count`·`byDifficulty`·`byContribution`·`totalVolume` 동일).
  - **per-result 원소별 1:1**: `summary.count === results.length`, `summary.byDifficulty[d]` == `results` 중 `difficulty===d` 원소 수(모든 `d ∈ DIFFICULTIES`), `summary.byContribution[c]` == `results` 중 `contribution===c` 원소 수(모든 `c ∈ CONTRIBUTION_LEVELS`), `summary.totalVolume` == `results` 의 `volume` 합산(본 task 는 spec-로컬 독립 재유도와의 1:1 만 단언, 집계 로직 자체 재구현 0).
  - **전 enum 슬롯 존재 boundary**: `Object.keys(summary.byDifficulty)` set == `new Set(DIFFICULTIES)`(3 슬롯), `Object.keys(summary.byContribution)` set == `new Set(CONTRIBUTION_LEVELS)`(4 슬롯) — 미등장 분류도 키 존재·값 0(표현 layer 슬롯 누락 0). difficulty/contribution 전 슬롯을 cover 하는 multi-slot·반복-슬롯 results 합성으로 일반화 단언.
  - **raw-not-stored boundary**(REQ-032) — `summary` 의 key set 이 `{count, byDifficulty, byContribution, totalVolume}` 와 set-equal, `narrative` 본문·raw 활동 본문 key 부재(EvaluationResult.narrative 가 summary 로 새지 않음).
  - 이 1:1 이 aggregator 가 resolve 로 thread 하는 **그 동일 `runPlan` 의 publish-leg** 에서 나온다(`report.summary` 가 `commandArgs`·`descriptor` 와 같은 `buildRealDataResultIssueCommandPlan(results, runPlan.run)` 산물, 17-way 묶음 항).

직전 sibling 들은 이 summary 내부-shape per-result 집계 축을 aggregator convergence closure 에 합류시키지 않았다:
- **T-0786 (aggregator 17-way)**: evaluation-leg input 내부-shape 1:1(activities[i] 필드별) + 16축을 묶었으나 **publish-leg summary 내부의 집계 깊이는 미합류**(publish.report.summary 자체를 top-level deep-equal·credential surface 로만 다룸).
- **T-0776 (aggregator 7-way)**: `stepArgs.publish.report.summary == buildRealDataResultIssueCommandPlan(results, runPlan.run).report.summary` top-level deep-equal(`toEqual`) + **특정 3-result fixture** 의 고정-리터럴 슬롯값(`byDifficulty.easy===1`·`byContribution.high===1` 등, 373~379행)·`count===results.length`·`totalVolume===10`(370~371행)만 — 임의 `results[]` 에서의 **원소별 슬롯 +1 1:1 재유도·전 enum 슬롯 존재(미등장 0)·multi-slot/반복-슬롯 일반화·volume 합산 불변식** 단언 0(한 고정 fixture 의 슬롯값 점검에 그침).
- **T-0777~0785 (aggregator 8~16-way)**: publish-leg summary 내부 집계 미합류 또는 descriptor.body/command-args/search/resolve/collect-leg 축만 — summary 집계 깊이 1:1 합류 0.
- **result-summary helper spec / report-plan helper spec**: `buildRealDataResultSummary`(T-0580) + `assertRealDataResultSummaryConsistentWithInputs`(T-0705) self-guard·spec 가 count·분포·totalVolume 집계를 박제했으나 **aggregator(`buildRealDataE2eStepArgs`) chain 진입·resolve·post 미합류**(집계 빌더 단독 spec — aggregator 산출 summary 의 내부-shape ↔ results 원소별 1:1 종단 정합 0).

본 task 는 그 빈 자리를 채워 **aggregator 가 산출한 publish-leg report.summary(RealDataResultSummary)가 검증 source results[] 로부터 production buildRealDataResultSummary 와 필드별 byte-identical·원소별 1:1 집계(전 enum 슬롯 존재/미등장 0, volume 합산, narrative key 부재) 임을, summary top-level 재유도·evaluation-leg·collect-leg·descriptor·command-args·resolve·post 와 묶어 closure 에 합류**시킨다. 단일 source `(seeds, modelId, run, activities, results, search-stdout, exec-stdout)` 로부터:

1. **publish-leg summary 내부-shape per-result 1:1 집계 thread(축 18, 본 task 의 새 표면)** — `stepArgs = buildRealDataE2eStepArgs(runPlan, activities, results)` → `stepArgs.publish.report.summary` 가 `buildRealDataResultSummary(results)`(production 위임 직접 호출) 와 byte-identical deep-equal(`toEqual`), `count`/`totalVolume` 각 `toBe`(spec-로컬 독립 재유도값과), 모든 `d ∈ DIFFICULTIES` 에 `byDifficulty[d]` == 독립 재유도 카운트, 모든 `c ∈ CONTRIBUTION_LEVELS` 에 `byContribution[c]` == 독립 재유도 카운트, key set == `{count,byDifficulty,byContribution,totalVolume}` set-equal(narrative 부재), 슬롯 key set == enum set-equal(전 슬롯 존재/미등장 0). difficulty 3 슬롯·contribution 4 슬롯 모두 등장·일부 반복하는 multi-slot results 합성.
2. **publish-leg summary top-level 재유도(축 7, 7-way 묶음 항)** — `stepArgs.publish.report.summary` 가 byte-identical deep-equal `buildRealDataResultIssueCommandPlan(results, runPlan.run).report.summary`(command-plan 경유 — aggregator 와 동일 위임 SSOT).
3. **evaluation-leg input 내부-shape 1:1(축 17 묶음 항)** — `stepArgs.evaluation.inputs[i]` 가 `mapActivityToEvaluationInput(activities[i])` 와 필드별 byte-identical(unitId 합성·contributionKind R-30·metadata reference·raw key 부재).
4. **collect-leg serviceIdentities 내부-shape + collectCallArgs top-level 재유도(축 16 묶음 항)** — `collectCallArgs[i].person.serviceIdentities` 가 `seeds[i]` `{service,externalId}` 추림과 1:1, `collectCallArgs == buildRealDataCollectCallArgs(seeds)`.
5. **inputs top-level 재유도 + callArgs.input 페어링(묶음 항)** — `inputs == buildRealDataEvaluationInputs(activities)`, `callArgs[i].input === inputs[i]`.
6. **search-json-fields↔parse-shape set-equal + number thread(묶음 항)** — `searchArgv[6]` split 집합 == `REAL_DATA_RESULT_ISSUE_SEARCH_PARSE_SHAPE_KEYS` == 실 파싱 hit 키 set-equal, number N → resolve → post.
7. **collect/evaluate modelId 공유(묶음 항)** — `runPlan.pipeline.modelId === modelId === callArgs[i].options.modelId`.
8. **search-argv 전체-벡터 + resolve-argv create/update(묶음 항)**.
9. **publish-leg command-args-labels + title/body 두 경로 + descriptor 재유도(묶음 항)**.
10. **marker 3-축 + resolve issueNumber + post run-identity(종단)**.

이 18-way(publish-leg summary 내부-shape per-result 1:1 집계 + summary top-level 재유도 + evaluation-leg input 내부-shape + collect-leg serviceIdentities 내부-shape + collectCallArgs top-level 재유도 + inputs top-level + callArgs.input 페어링 + collect/evaluate modelId 공유 + search-json-fields↔parse-shape set-equal + number thread + search-argv 전체-벡터 + resolve-argv create/update + command-args labels + title/body 두 경로 + descriptor 재유도 + marker 3-축 + resolve issueNumber + post run-identity)가 **검증 source `(seeds, modelId, run, activities, results)`** single-source 로 수렴함이 **search-or-update 멱등성**(REQ-009)·**raw 미보유 평가 결과 정합**(REQ-032)·**난이도/기여도 정성 분류 집계 정합**(REQ-037/038)·**raw 미저장**(REQ-059)의 aggregator-level "aggregator 가 step④ 이슈로 박제할 결과 요약 1건의 정량 집계(평가 단위 수·난이도 분포·기여도 분포·총 volume)가 검증 source 평가 결과 집합과 원소별 어긋남 0, 미등장 분류도 슬롯 보존, narrative raw 는 요약으로 새지 않음" 의 종단 닫음이다. **e2e 의 publish-leg 가 검증 source results 의 EvaluationResult[]→RealDataResultSummary 집계 깊이까지 단일 검증 source 에서 원소별 1:1 로 맞물리는 seam slice** 다(collect-leg·evaluation-leg 내부-shape 에 이어 publish-leg 내부-shape — runPlan 세 leg 의 내부-shape 깊이 closure 완성).
