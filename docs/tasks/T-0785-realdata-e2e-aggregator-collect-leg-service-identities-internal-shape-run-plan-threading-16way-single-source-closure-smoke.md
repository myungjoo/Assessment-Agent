# T-0785 — realdata-e2e step④ aggregator collect-leg serviceIdentities 내부-shape 1:1 thread 합류 16-way single-source closure non-gated build-time smoke 신설

## Why

PLAN.md §109(🟢 실 평가 e2e, P5)의 build-time 순수 layer 는 최외곽 단일 진입 `buildRealDataE2eRunPlan(seeds, modelId, run)` → `{pipeline, run}`(T-0597)을 산출하고, 그 `runPlan` 을 pre-실행 aggregator `buildRealDataE2eStepArgs(runPlan, activities, results)` → `{evaluation, publish}`(T-0601)에 통째로 넘긴다. 직전 sweep(T-0778~0784)은 aggregator 산출의 evaluation-leg + publish-leg + collect-leg **표면**을 단일 source 로 묶어 15-way 를 완성했고, 특히 T-0783(14-way)이 collect-leg `runPlan.pipeline.collectCallArgs` 의 **top-level deep-equal**(`collectCallArgs == buildRealDataCollectCallArgs(seeds)`)을, T-0784(15-way)가 search 요청-필드↔추출-shape set-equal 을 합류시켰다.

그러나 collect-leg 의 **내부-shape 깊이**(Person → ServiceIdentity 배열 차원)에는 15-way 가 닫지 않은 seam 이 남아있다 — aggregator 가 산출한 `runPlan.pipeline.collectCallArgs[i].person.serviceIdentities`(실 step② `collectForPerson(person, since, assessmentId)` 의 첫 인자 `person` 안 ServiceIdentity 배열, 각 원소가 `{service, externalId}` 쌍 — `CollectForPersonInput.serviceIdentities = Pick<ServiceIdentity, "service" | "externalId">[]`)가, 검증 source `seeds[i].serviceIdentities`(각 `RealDataServiceIdentitySeed` 가 `{service, externalId, isPrimary}` 보유)의 **`{service, externalId}` 쌍 배열과 원소별·필드별 byte-identical 1:1**(service 필드 + externalId 필드 동시, 모든 원소, multi-identity Person 포함)임은 aggregator+resolve 종단 closure 에 미합류다.

collect-leg serviceIdentities 내부-shape 축은 15-way 가 잡은 15축과 distinct 한 표면이다:

- **collect-leg serviceIdentities 내부-shape 1:1 thread 축(본 task 의 새 표면)** — aggregator 가 `buildRealDataE2eRunPlan` 위임 `buildRealDataPipelinePlan`(T-0592) 경유 `buildRealDataCollectCallArgs(seeds)`(T-0577) → `buildRealDataCollectInput(seeds)`(T-0581) 로 산출한 `collectCallArgs[i].person.serviceIdentities` 가:
  - `seeds[i].serviceIdentities` 의 각 원소를 `{service, externalId}` 로 추린 배열과 **원소별·필드별 byte-identical**(길이 동일·순서 보존·각 원소 `service`+`externalId` 둘 다 동일).
  - **multi-identity Person**(한 Person 이 ServiceIdentity 2+ 보유)에서도 모든 원소가 1:1 보존(첫 원소만이 아님 — T-0783 은 `[0].externalId` scalar 만 sanity).
  - `seeds[i].serviceIdentities[*].isPrimary` 필드는 `CollectForPersonInput` 최소 shape 로 추려지며 **누락**(collectCallArgs person 에 isPrimary 미surface — REQ-024 의 primary 표식이 수집 호출-args 로 새지 않음을 boundary 로 단언).
  - 이 1:1 이 aggregator 가 evaluate/publish 로 thread 하는 **그 동일 `runPlan` 의 collect-leg** 에서 나온다 — 즉 aggregator 가 step② 로 넘길 Person 식별자(service+externalId 쌍, ADR-0030 §2 author 귀속 key)가 검증 source seed 와 어긋남 0.

직전 sibling 들은 이 serviceIdentities 내부-shape 1:1 축을 aggregator convergence closure 에 합류시키지 않았다:
- **T-0784 (aggregator 15-way)**: search-json-fields↔parse-shape set-equal + number→resolve→post + collect-leg top-level 재유도 + 13축을 묶었으나 collect-leg 내부의 **serviceIdentities 배열 깊이는 미합류**(collectCallArgs 자체를 deep-equal 의 한 묶음으로만 다룸).
- **T-0783 (aggregator 14-way)**: `collectCallArgs == buildRealDataCollectCallArgs(seeds)` top-level deep-equal(`toEqual`) + 원소별 `since===undefined`·`assessmentId===placeholder` + `collectCallArgs[i].person.serviceIdentities[0].externalId === seeds[i].serviceIdentities[0].externalId`(373~378행, **첫 identity·externalId scalar 단일 필드 sanity 만**) — serviceIdentities 배열 전체·service 필드 동시·multi-identity 원소별 1:1 byte-identical 단언 0.
- **T-0775~0782 (aggregator 4~13-way)**: collect-leg 미합류 또는 search-argv/resolve/descriptor/inputs 축만 — serviceIdentities 내부-shape 1:1 합류 0.
- **collect-input/collect-call-args self-guard·spec**: `buildRealDataCollectInput`(T-0581) + `assertRealDataCollectCallArgsConsistentWithSources`(T-0688 self-wire) 가 serviceIdentities `{service, externalId}` 매핑·빈-가드를 박제했으나 **aggregator(`buildRealDataE2eStepArgs`/`buildRealDataE2eRunPlan`) chain 진입·resolve·post 미합류**(빌더/매퍼 단독 self-guard — aggregator 산출 collectCallArgs 의 내부-shape ↔ seed 1:1 종단 정합 0).
- **seed-fixture spec**: `RealDataSeedDescriptor`/`RealDataServiceIdentitySeed` shape 단독 spec — aggregator collect-leg 로의 1:1 thread 미합류.

본 task 는 그 빈 자리를 채워 **aggregator 가 산출한 collect-leg collectCallArgs[i].person.serviceIdentities 가 검증 source seeds[i].serviceIdentities 의 {service,externalId} 쌍 배열과 원소별·필드별 1:1(multi-identity Person 포함) byte-identical 임을, collect-leg top-level 재유도·evaluate-leg·publish-leg·resolve·post 와 묶어 closure 에 합류**시킨다. 단일 source `(seeds, modelId, run, activities, results, search-stdout, exec-stdout)` 로부터:

1. **collect-leg serviceIdentities 내부-shape 1:1 thread(축 16, 본 task 의 새 표면)** — `runPlan = buildRealDataE2eRunPlan(seeds, modelId, run)` → `runPlan.pipeline.collectCallArgs[i].person.serviceIdentities` 가 `seeds[i].serviceIdentities.map(si => ({service: si.service, externalId: si.externalId}))` 와 원소별·필드별 byte-identical(`toEqual`), 길이 == `seeds[i].serviceIdentities.length`, 순서 보존, 각 원소 `service`+`externalId` 둘 다 동일. multi-identity Person seed 로도 모든 원소 1:1. `isPrimary` 필드 미surface(`person.serviceIdentities[k]` 에 `isPrimary` key 부재).
2. **collect-leg call-args top-level 재유도(축 15, 14-way 묶음 항)** — `runPlan.pipeline.collectCallArgs` 가 byte-identical deep-equal `buildRealDataCollectCallArgs(seeds)`, 원소별 `since===undefined`·`assessmentId===ASSESSMENT_ID_PLACEHOLDER`·길이==seeds.length.
3. **search-json-fields↔parse-shape set-equal + number thread(축 14~15 묶음 항)** — `stepArgs.publish.searchArgv[6]` split 집합 == `REAL_DATA_RESULT_ISSUE_SEARCH_PARSE_SHAPE_KEYS` 집합 == 실 파싱 hit 키 집합 set-equal, parse-shape number(N) → resolve issueNumber → argv[2] → post issueNumber thread.
4. **collect/evaluate modelId 공유(묶음 항)** — `runPlan.pipeline.modelId === modelId === stepArgs.evaluation.callArgs[i].options.modelId`.
5. **search-argv 전체-벡터 위치-정합(묶음 항)** — `stepArgs.publish.searchArgv` byte-identical `["search","issues","--match","body",commandArgs.searchQuery,"--json","number,title,body","--limit","30"]`.
6. **resolve-argv update/create 위치-정합(묶음 항)** — hit N → `["issue","edit",String(N),"--title",updateArgs.title,"--body",updateArgs.body]`, hit 0 → `["issue","create",...createArgs,...labels]`.
7. **publish-leg command-args-labels + title/body 두 경로 + descriptor·summary 재유도(묶음 항)** — `createArgs.labels` deep-equal `["realdata-e2e","result"]`, `{title,body}` == `descriptor.{title,body}`, summary 재유도.
8. **evaluation-leg inputs 재유도 + 페어링(묶음 항)** — `inputs == buildRealDataEvaluationInputs(activities)`, `callArgs[i].input === inputs[i]`.
9. **marker 3-축 + resolve issueNumber + post run-identity(종단)** — `descriptor.marker === commandArgs.searchQuery === searchArgv[4]`, resolve issueNumber → post run token 전파.

이 16-way(collect-leg serviceIdentities 내부-shape 1:1 + collectCallArgs top-level 재유도 + search-json-fields↔parse-shape set-equal + number thread + collect/evaluate modelId 공유 + search-argv 전체-벡터 위치-정합 + resolve-argv 위치-정합 + command-args labels 고정상수 + command-args title/body 두 경로 + descriptor.{title,body} 재유도 + summary + inputs + callArgs.input 페어링 + marker 3-축 + resolve issueNumber + post run-identity)가 **검증 source `(seeds, modelId, run, activities, results)`** single-source 로 수렴함이 **search-or-update 멱등성**(REQ-009)·**1 Person 당 1 primary identity invariant 의 수집-경계 정합**(REQ-024)·**raw 미보유 평가 입력/결과 집계 정합**(REQ-032)·**author 귀속 key(externalId) 정합**(REQ-047)의 aggregator-level "aggregator 가 step② 로 넘길 Person 식별자(service+externalId 쌍)가 검증 source seed 와 원소별·필드별 어긋남 0, isPrimary 같은 비-수집 필드는 호출-args 로 새지 않음" 의 종단 닫음이다. **e2e 의 collect-leg 가 검증 source seed 의 Person→ServiceIdentity 배열 깊이까지 단일 검증 source 에서 1:1 로 맞물리는 seam slice** 다.

gap 확인(git grep, origin/main ac347053): aggregator-* sweep smoke 15파일(4~15-way) 중 serviceIdentities 참조는 14-way(T-0783) 1파일뿐이고 그 안 단언은 `collectCallArgs[i].person.serviceIdentities[0].externalId` scalar(첫 identity·externalId 단일 필드 sanity, 373~378행)만 — serviceIdentities 배열 전체(모든 원소)·service 필드 동시·multi-identity Person 의 원소별·필드별 byte-identical 1:1 단언 0. `aggregator-*service-identit* / *collect-leg-shape* smoke 파일 부재` + `git log origin/main` 동일 영역 박제 commit 0. live leg(실 prisma·실 collectForPerson·실 github.com fetch·실 LLM scoring·실 gh CLI 실행·DB·LAN gate) 복제 0·non-gated 항상 실행 — 순수 build-time in-memory 검증만.

- [ ] **Happy-path aggregator 16-way chain 합성**: 단일 source — `seeds: RealDataSeedDescriptor[]`(여러 Person 원소, **그 중 1+ Person 은 serviceIdentities 2+ 보유한 multi-identity**, 다양한 service/externalId) + 임의 양수 `modelId`(비-empty) + `run: {gitSha, dateToken}`(비-empty) synthetic literal, `activities: Activity[]`(여러 원소) + `results: EvaluationResult[]`(여러 원소) synthetic literal, 임의 양수 `N`. 다음을 한 chain 으로 호출: `runPlan = buildRealDataE2eRunPlan(seeds, modelId, run)` → `stepArgs = buildRealDataE2eStepArgs(runPlan, activities, results)` → `searchStdout`(N 담은 hit JSON 배열) → `parsedHits = parseRealDataResultIssueSearchOutput(searchStdout)`(1+ hit) → `resolvePlan = resolveRealDataResultIssueGhCommandPlan(searchStdout, stepArgs.publish.commandArgs)`(update 분기) → `execStdout`(`/issues/N` URL) → `outcomeReport = buildRealDataResultOutcomeStepArgs(runPlan, execStdout)`. 산출물이 모두 정상(runPlan.pipeline.collectCallArgs 비어있지 않은 배열·길이==seeds.length, 각 person.serviceIdentities 비어있지 않은 배열, stepArgs 정상, parsedHits·resolvePlan·outcomeReport 정상) happy test 1+.
- [ ] **collect-leg serviceIdentities 내부-shape 원소별·필드별 1:1 수렴(branch — 핵심 불변식, 본 task 의 새 표면)**: 모든 i 에 대해 `runPlan.pipeline.collectCallArgs[i].person.serviceIdentities` 가 `seeds[i].serviceIdentities.map(si => ({service: si.service, externalId: si.externalId}))` 와 byte-identical deep-equal(`toEqual`) 임을 단언 1+ test. 추가로: 길이 == `seeds[i].serviceIdentities.length`(`toHaveLength`), 각 원소 `person.serviceIdentities[k].service === seeds[i].serviceIdentities[k].service`(`toBe`, forEach)·`person.serviceIdentities[k].externalId === seeds[i].serviceIdentities[k].externalId`(`toBe`, forEach), 순서 보존(인덱스 정합). **단언 shape·필드명은 collect-input helper(59~69행) 및 `CollectForPersonInput`(25행) 시그니처로 확인해 정확히 박제** — 형식이 다르면 helper 기준으로 조정(본문에 사유 명시).
