# T-0792 — realdata-e2e step④ deploy/daily-test.sh black-box HTTP step 계약(health·liveness·auth) ↔ 실 NestJS controller route decorator(path·method·status) parity drift-detection non-gated build-time smoke 신설

## Why

PLAN.md §109(🟢 실 평가 e2e, P5)의 step④는 `deploy/daily-test.sh` 가 매일 02:00 자율 nightly black-box HTTP 스모크로 **기동된 컨테이너를 :3000 으로 두드려** 앱이 살아있고 핵심 계약이 보존됐는지 검증한다(헤더 6~9행: step health `GET /api == "Assessment-Agent"`, step liveness `GET /api 일치 + GET / == 200 + SPA HTML`, step auth `POST /api/users(201|409) → POST /api/auth/login(200) → GET /api/auth/me(200)`). 즉 daily-test.sh 가 검사하는 **HTTP step 계약(endpoint path·HTTP method·기대 status code)은 실 NestJS controller 가 노출하는 route 와 정합해야 하는 운영 contract** 다 — controller 의 route path/method/status 가 silent 하게 drift 하면(예: `@HttpCode(201)`→default 200·path rename·method swap·`@Controller` prefix 변경) daily-test.sh 의 하드코딩된 black-box 호출이 **실 route 와 어긋나 nightly 가 false-FAIL** 을 내고 무인 모니터링에 잘못된 신호를 준다(REQ-009 search-or-update 멱등 e2e 가 의도대로 돌고 그 결과가 올바로 보고되는가의 운영 무결성, REQ-061 smoke-in-CI).

직전 sweep 들은 build-time 순수 seam 을 차례로 닫았다 — in-memory aggregator render-line(T-0778~0789, 20-way, 소진), shell `step_eval` ↔ TS helper jest argv full-vector parity(T-0790), shell 머신 요약 JSON 스키마 contract(T-0791). **T-0791 Follow-up 은 다음 잔여 distinct build-time seam 후보 (a) "`deploy/daily-test.sh` 의 step_health/step_liveness/step_auth 가 두드리는 HTTP endpoint·기대 상태 ↔ 실 NestJS controller route/응답 contract parity(genuine 한지·controller route 가 실제로 존재하는지 HIGH bar 재판정 필요)" 를 명시**했다. 본 task 는 그것을 HIGH-bar 로 재판정해 채택한다 — genuine distinct seam 임을 사전 조사로 확인했다.

본 task 의 사전 조사(origin/main e99bd2b7) 결과 — (1) **daily-test.sh 의 HTTP step 계약이 두드리는 route 가 전부 실존·안정** 하고, (2) **그 계약을 실 controller decorator 와 대조하는 build-time smoke 는 0 부재** 다:

- **route 실존 확인** (HIGH bar 통과의 핵심 — make-work 가 아님):
  - `GET /api` → `src/app.controller.ts` `@Controller("api")` + `@Get()` (getRoot) → `src/app.service.ts` `getStatus()` 가 `APP_STATUS_MESSAGE = "Assessment-Agent"` 반환. daily-test.sh 의 `HEALTH_MESSAGE="Assessment-Agent"`(43행)·step_health(75·80행)·step_liveness(92~93행)와 정합.
  - `GET /` → P6 WebModule serve-static(SPA HTML) — daily-test.sh step_liveness(97~106행 `GET / == 200 + SPA HTML`). (controller route 가 아닌 serve-static 이라 본 task 는 path·status 만 정적 단언, SPA HTML 내용은 Out-of-Scope.)
  - `POST /api/users` → `src/user/user.controller.ts` `@Controller("api/users")` + `@Post()` + `@HttpCode(201)`, service P2002(email @unique) → ConflictException(409). daily-test.sh step_auth signup(117~122행 `201|409`)와 정합(멱등 첫 호출 201·재호출 409).
  - `POST /api/auth/login` → `src/auth/auth.controller.ts` `@Controller("api/auth")` + `@Post("login")` + `@HttpCode(200)`. daily-test.sh step_auth login(125~129행 `== 200`)와 정합.
  - `GET /api/auth/me` → `src/auth/auth.controller.ts` `@Get("me")`. daily-test.sh step_auth me(132~136행 `== 200`)와 정합.
- **build-time cross-artifact smoke 0 부재** — `test/smoke/` grep 결과 기존 daily-test smoke 2개(`...step-eval-shell-argv...`(T-0790)·`...machine-result-json-schema...`(T-0791))는 각각 step_eval jest argv·머신 요약 JSON 스키마만 cover 하고 **step_health/step_liveness/step_auth 의 HTTP 계약(path·method·status)을 실 controller route decorator 와 대조 0**. e2e(`test/e2e/auth.e2e-spec.ts`·`users.e2e-spec.ts`)는 실 route 동작을 검증하나 **gated DB-bound**(globalSetup postgres 필요)이고 daily-test.sh 의 shell 계약 텍스트를 읽지 않으므로 shell 사본↔controller 정본 drift 를 못 잡는다.

즉 **실 `deploy/daily-test.sh` 의 black-box HTTP step 계약(하드코딩된 path·method·기대 status)을 정적 추출해, 실 NestJS controller 소스(`@Controller` prefix + `@Get`/`@Post` route + `@HttpCode`/HttpStatus + `APP_STATUS_MESSAGE`)에서 조립한 full-path·method·status 와 byte-identical/1:1 정합임을 단언하는 build-time smoke 가 0 부재** 다. 이 contract 가 drift 하면(예: 누군가 user.controller 의 `@HttpCode(201)` 를 빼서 default 200 으로 만들거나, auth route prefix 를 바꾸거나, login 을 GET 으로 바꾸거나) daily-test.sh 의 하드코딩 호출이 silent 분기 → nightly 자율 모니터링 false 신호. 이는 render-line(in-memory) · step_eval argv(T-0790) · machine-JSON 스키마(T-0791)와 distinct 한, **shell-HTTP-contract↔controller-route-decorator** 표면이다.

본 task 는 그 빈 자리를 채운다 — `deploy/daily-test.sh` + 4 controller/service 소스 파일을 `readFileSync` 로 읽어, (a) shell 측 5 HTTP 계약 endpoint 의 path·method·기대 status 추출, (b) controller 측 `@Controller` prefix + route decorator + `@HttpCode`/status + status-message 추출, (c) shell full-path == controller 조립 full-path byte-identical·method 1:1·기대 status 정합을 단언한다.

live leg(실 컨테이너·실 HTTP·실 DB·실 NestJS 부팅) 복제 0·non-gated 항상 실행 — 순수 build-time 검증만(파일 read + 정적 텍스트 추출). shell·controller 파일은 읽기만 하고 실행/import/부팅 0(NestJS 모듈 import 0 — readFileSync 텍스트 read only, DB-free).
