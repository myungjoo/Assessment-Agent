# T-0938 — realdata-e2e dual-leg run report cross-publish marker anchor stability single-source convergence non-gated smoke

## Why

PLAN.md 109행 (🟢 실 평가 e2e, P5) step④ (daily-test dual-leg run 결과 rolling-issue 멱등 박제) chain 의 **같은 run 을 여러 밤 연속 publish 할 때, 다음 밤 그 rolling-issue 를 재발견(re-find)하는 검색 identity anchor(`descriptor.marker` = `commandArgs.searchQuery`)가 어긋나지 않고 안정하며, 나아가 1차 create publish 의 body 에 심긴 marker 라인이 2·3차 publish 의 검색 anchor 와 정확히 같아 재발견 loop 이 실제로 닫힘** — 이 아직 어떤 smoke 에도 chain 그물로 묶이지 않았다.

REQ-009 멱등("동일 run 의 기존 이슈를 찾아 갱신, 중복 생성 안 함")의 cross-publish 안정성은 **세 매체(medium)** 위에 얹혀 있다:

- **issueNumber 축 — 편집 대상(republish T-0922 가 봉합)** — 1차 create publish 가 낳은 이슈 번호 M 이 2차 publish 의 search-hit 로 다시 관통해 `plan.action.update.issueNumber === M` / `plan.argv[2] === String(M)` 로 좁혀져 2차가 그 이슈 M 을 **정확히 갱신**한다. republish 는 이 **번호 state-transition** 을 자산화한다.
- **url 축 — 사람 링크(permalink T-0937 이 봉합)** — 사람이 여는 `outcome.url` 이 1차 create 와 이후 모든 update 에서 byte-identical 하게 같은 `.../issues/M` 을 가리킨다. permalink 는 이 **사람-링크 안정성** 을 자산화한다.
- **marker 축 — 검색 anchor(본 task 가 봉합)** — 위 두 축은 모두 **"2차 밤에 그 이슈를 다시 찾을 수 있다"** 를 전제로 성립한다. 그 재발견은 `commandArgs.searchQuery`(=`descriptor.marker`, run-token 종속) 로 GitHub 을 검색해 body 에 marker 를 담은 이슈를 hit 하는 것으로 이뤄진다. 따라서 재발견이 성립하려면 (a) 검색 anchor(searchQuery)가 1차·2차·3차 publish 에서 **byte-identical 하게 안정**(같은 run 이므로 marker 도 같음)해야 하고, (b) 1차 create publish 가 이슈 body 에 심은 marker 라인이 2·3차 publish 의 searchQuery 와 **정확히 같아야** 한다 — 그래야 2차 검색이 1차가 만든 그 이슈를 hit 하고(`hit.body.includes(searchQuery)`), resolve 가 create 아닌 **update** 로 좁혀진다.

즉 **marker anchor 안정성 + publish→re-search round-trip 닫힘** 이 rolling-issue 멱등의 **재발견 무결성** 이고, issueNumber(T-0922)·url(T-0937) 두 축이 **암묵적으로 의존하지만 아무도 명시적으로 못 박지 않은** load-bearing 축이다. 만약 마커가 밤마다 흔들리거나(예: run-token 종속이 아니라 timestamp 종속이 되면) 1차 create body 의 marker 가 2차 searchQuery 와 어긋나면 — 2차 검색이 1차 이슈를 못 찾아 resolve 가 **새 이슈를 create** 하고, rolling-issue 멱등이 근본에서 무너진다(중복 이슈 생성). 이 안정성의 load-bearing 근거는 literal 하드코딩이 아니라 **descriptor.marker 가 run 식별(gitSha/dateToken)에서 파생돼 같은 run 이면 같은 marker** 라는 단일 source 성이다.

그러나 이 **cross-publish marker anchor stability single-source(및 round-trip 닫힘)** 를 어느 smoke 도 검증하지 않는다:

- 형제 republish(T-0922, create→update idempotency)는 1차 create-output 의 M 이 2차 search-input 으로 threading 해 2차 resolve 가 `update`/M 으로 좁혀짐(**issueNumber state-transition**)만 자산화한다 — 2차 검색이 성립하는 **전제인 marker anchor 의 cross-publish 안정성**(1차 create body marker == 2차 searchQuery)은 미단언(번호 축 ≠ 검색 anchor 축).
- 형제 permalink(T-0937, cross-publish url permalink stability)는 세 publish 의 `outcome.url` 이 byte-identical(모두 `.../issues/M`)함(**사람-링크 안정성**)만 자산화한다 — url 은 execute-side output-parse 산물이고, 본 task 의 marker 는 pre-exec 검색 anchor 라 다른 축(사람 링크 ≠ 검색 anchor).
- 형제 T-0928(create-branch)/T-0929(update-branch)은 **한 publish chain 내부**에서 searchArgv(call 1 `--match body <marker>`)의 marker 와 그 chain 의 create/edit body 선두 marker 라인이 단일 source(descriptor.marker)로 byte-identical 함만 자산화한다 — **여러 publish 에 걸친**(1차 body marker == 2차 searchQuery) cross-publish round-trip 은 대상이 아니다(intra-chain ≠ cross-publish).
- 형제 T-0921(dual-medium orthogonal)은 **한 chain 내부**에서 marker(searchArgv 매체)와 issueNumber(editArgv 매체)가 서로 직교(cross-contamination 0)함만 자산화한다 — cross-publish 안정성·round-trip 닫힘과 무관.

본 task 는 그 **cross-publish marker anchor stability + round-trip 닫힘 seam** 을 닫는다 — cross-publish 안정 trilogy 의 **marker 축**(그리고 republish·permalink 가 의존하는 재발견 loop 의 load-bearing 축). chain: 두 leg outcome + run → report → descriptor → commandArgs 를 통과시켜 identity anchor `searchQuery`(=descriptor.marker)를 얻고, (1차) 빈 search(`"[]"`)로 create plan → create body(`createArgs.body`, marker 선두 라인 포함), (2·3차) **1차 create body 를 그대로 담은** search-hit(`[{"number":M,"title":descriptor.title,"body":createArgs.body}]`) → resolve(`hit.body.includes(searchQuery)` → update) → update plan 를 산출한 뒤, 세 publish 의 `searchQuery` 가 모두 byte-identical(=descriptor.marker) AND 1차 create body 의 marker 라인이 2·3차 searchQuery 와 정확히 같아 round-trip 이 닫힘(재발견이 vacuous 아님)을 박제한다.

(b) 그 1차 create body 를 그대로 담은 2·3차 search-hit 로 resolve 하면 `hit.body.includes(searchQuery)` 가 참이라 `plan2/plan3.action.action === "update"` 로 좁혀짐(round-trip 이 실제로 닫혀 재발견 성립) 1+. (c) **guard-against-vacuity**: 2차 search-hit body 를 marker 를 **제거한** 텍스트(예: `"무관 본문"`)로 바꾸면 `hit.body.includes(searchQuery)` 가 거짓이라 resolve 가 `"create"` 로 떨어짐(round-trip 이 깨지면 재발견이 실패해 신규 이슈를 만들려 함을 test 가 실제 감지 — 즉 (b) 의 update 단언이 vacuous 아님) 1+ test.
- [ ] **marker anchor single-source 단언 (핵심 3 — anchor 가 run-token 종속, literal 아님)** — (a) 1차 run 을 다른 값 `run2`(gitSha/dateToken 모두 다름, 서로 substring 아님)로 바꾼 재조립에서 세 publish 의 `searchQuery` 가 **함께** 새 marker 로 이동(원래 run 의 searchQuery 와 다름) AND 여전히 세 publish 상호 byte-identical 1+ test — 즉 검색 anchor 가 독립 고정 literal 이 아니라 **run 식별 단일 source 종속**. AND 새 marker 를 담은 create body 로 조립한 2·3차 hit 로도 round-trip 이 닫힘(update 로 좁혀짐, 새 run 에서도 재발견 성립) 1+. (b) `descriptor.marker` 를 우회해 임의 문자열을 searchQuery 로 직접 주입하는 경로가 없음(searchQuery 는 반드시 commandArgs 빌더가 descriptor.marker 로부터만 산출)을 commandArgs 산출로 확인 1+.
- [ ] **create/update 두 분기 대칭 + anchor 불변 단언 (branch)** — (a) 1차 plan1: `plan1.action.action === "create"`(빈 search 분기), 2·3차 plan2/plan3: `plan.action.action === "update"`(1차 body 담은 hit 분기)이더라도 세 publish 가 검색에 쓰는 anchor(`commandArgs.searchQuery`)는 **분기 선택과 독립**하게 동일 1+ test. (b) resolve 의 create/update 분기 판정 discriminant 가 `hit.body.includes(searchQuery)`(anchor 매체) 임을 빈 search(create)·marker-담은 hit(update)·marker-제거 hit(create) 세 stdout 으로 각각 확인 — anchor 안정성이 재발견 성패를 가르는 유일 매체임 1+.
- [ ] **run/leg outcome status 무관 — anchor 안정 단언 (branch)** — (a) 동일 run 고정, leg outcome 조합(eval pass/collect pass vs eval fail/collect skip)만 다르게 3-cycle 조립 → 세 publish 의 `searchQuery` 동일 + round-trip 닫힘 유지(marker 는 run 종속, leg status/overallStatus 무관) 1+ test. (b) 서로 다른 run 두 개(run_A `{gitSha:"abc1234", dateToken:"2026-07-11"}`, run_B `{gitSha:"def5678", dateToken:"2026-07-12"}`, 서로 substring 아님) → 각 run 의 세 publish searchQuery 는 run 내부에서 상호 byte-identical 이되 run_A 의 searchQuery !== run_B 의 searchQuery(anchor 가 run 을 구분) 1+ test.
- [ ] **Error path / negative cases 충분 cover** — 예외 분기마다 각 1+ test(단일 negative 금지):
