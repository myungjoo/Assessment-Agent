# T-0936 — realdata-e2e dual-leg run report output-parse url↔issueNumber intra-outcome cross-field single-source closure non-gated smoke

## Why

PLAN.md 109행 (🟢 실 평가 e2e, P5) step④ (daily-test dual-leg run 결과 rolling-issue 멱등 박제) chain 의 **execute-side output-parse 가 산출한 outcome 의 두 반환 필드가 서로 어긋날 수 없음** — 즉 `outcome.url` 과 `outcome.issueNumber` 가 **같은 execStdout URL 매칭 한 지점**에서 co-유도돼 상호 정합(url 이 issueNumber 를 포함) — 이 아직 어떤 smoke 에도 chain 그물로 묶이지 않았다.

output-parse 파서(`parseRealDataDailyStepDualLegRunReportIssueCreateEditOutput`)는 create/edit stdout 에서 issue URL `https://github.com/<owner>/<repo>/issues/<n>` **한 매칭**을 뽑아 그로부터 **두 필드를 동시에** 산출한다: `url`(그 매칭 전체) + `issueNumber`(그 url tail 의 번호 `<n>`). 즉 url 이 파서의 1차 추출이고 issueNumber 는 그 url 의 `/issues/<n>` segment 를 투영한 값이다. 두 필드는 **하나의 source(그 URL 매칭)** 에서 나오므로 구조적으로 서로 어긋날 수 없다 — `outcome.url` 은 정확히 `.../issues/${outcome.issueNumber}` 로 끝나야 하고, url 의 번호 segment 는 `String(outcome.issueNumber)` 와 byte-identical 이어야 한다.

이 intra-outcome cross-field 정합이 rolling-issue 멱등(REQ-009)의 execute-side 무결성의 마지막 그물이다: outcome 은 다음 밤 추적의 기준(issueNumber = 다음 밤 검색·갱신 대상, url = 사람이 여는 링크)으로 쓰이는데, 만약 파서가 issueNumber 를 한 URL 에서 뽑고 url 을 **다른 문자열**에서 뽑는 버그가 생기면(예: url 필드에 raw stdout 의 무관한 링크가 새고 issueNumber 만 정확) — outcome.url(사람이 여는 링크)이 outcome.issueNumber(다음 밤 검색 대상)와 다른 이슈를 가리켜 rolling-issue 추적이 조용히 어긋난다. 두 필드가 **같은 URL 한 지점에서만** 유도됨을 chain 그물로 못 박아야 이 divergence 가 원천 차단된다.

그러나 이 **output-parse url↔issueNumber intra-outcome cross-field single-source** 를 어느 smoke 도 검증하지 않는다:

- 형제 T-0935(create-branch output-parse issueNumber **genesis**)는 create 분기에서 갓 생성된 번호 M 이 오직 execStdout URL(실행 후)에서만 태어나고 pre-exec create chain 엔 전무함(issueNumber 의 **출처/provenance**)만 자산화한다 — outcome 의 **다른 반환 필드 url 과의 상호 정합**은 대상이 아니다(genesis 는 M 이 어디서 오는가, 본 task 는 url 과 issueNumber 가 서로 일치하는가).
- 형제 T-0920(edit-branch output-parse issueNumber convergence)은 update 분기에서 기존 번호 N 이 search-hit→resolve→`plan.argv[2]`→output-parse 4지점 수렴함(issueNumber 의 **pre/post-exec 관통**)만 자산화한다 — 마찬가지로 url↔issueNumber 상호 정합은 축이 아니다.
- 형제 output-stdout-value-consistency(T-0924)는 outcome **전체 값**(issueNumber + url)이 raw stdout 으로부터 **독립 재유도한 expected 와 deep-equal** 임만 자산화한다 — 각 필드를 stdout 과 **개별** 대조할 뿐, **두 필드 상호간의** cross-field 불변(url ⊇ issueNumber)을 직접 못 박지 않는다(외부 stdout 대조 축 ≠ intra-outcome 내부 정합 축).
- 형제 outcome-parse-shape(T-0923)은 outcome 의 **own-key set** 이 선언 shape `["issueNumber","url"]` 와 set-equal 임(**키 집합**)만 자산화한다 — 두 키의 **값 상호 관계**는 대상이 아니다.

본 task 는 그 **intra-outcome url↔issueNumber cross-field single-source seam** 을 닫는다 — issueNumber 축(T-0935 genesis + T-0920 convergence)의 **url 짝**. chain: 두 leg outcome + run → report → descriptor → commandArgs 를 통과시켜 유효 commandArgs 를 얻고, (i) 빈 search(`"[]"`)로 create plan → create execStdout(`.../issues/M`) → output-parse → outcome, (ii) marker-매칭 hit 로 update plan → edit execStdout(`.../issues/N`) → output-parse → outcome 두 분기 각각에서 `outcome.url` 이 정확히 `.../issues/${outcome.issueNumber}` 로 끝나고 url 의 번호 segment === `String(outcome.issueNumber)` 임을 박제한다.

issue-still-relevant 확인(2026-07-12): `ls test/smoke | grep dual-leg | grep -iE "url.*issuenumber|issuenumber.*url|cross-field"` = **0개**(url↔issueNumber intra-outcome cross-field seam 미봉합). `git log origin/main` 동일 영역(dual-leg output-parse url cross-field smoke) 박제 commit 0. output-parse 파서(`parse...IssueCreateEditOutput`, T-0903)·종단 컴포저(T-0902)·argv 빌더(T-0899) 배선은 이미 main 에 박제됨 — 본 task 는 그 배선을 **다시 만들지 않고** outcome 의 두 반환 필드 cross-field 정합을 대조하는 **smoke 그물만** 신설.
