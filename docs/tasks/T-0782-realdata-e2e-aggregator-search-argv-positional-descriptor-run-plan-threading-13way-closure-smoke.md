# T-0782 — realdata-e2e step④ aggregator search-argv 전체-벡터 위치-정합 합류 13-way single-source closure non-gated build-time smoke 신설

## Why

PLAN.md §109(🟢 실 평가 e2e, P5)의 step④ 멱등 search-or-update 의 build-time 순수 layer 는 **검증된 단일 run plan(`buildRealDataE2eRunPlan(seeds, modelId, run)` → `{pipeline, run}`, T-0597)을 pre-실행 aggregator(`buildRealDataE2eStepArgs(runPlan, activities, results)` → `{evaluation, publish}`, T-0601)에 통째로 넘긴다**. 이 aggregator 의 `.publish` leg 는 `RealDataResultIssuePublishPlan {report, commandArgs, searchArgv}` 세 컴포넌트를 산출한다. 직전 sweep(T-0778~0781)은 publish leg 의 **command-args 객체 surface(body·title·labels)** 와 그 필드값들이 조립되는 **resolve-argv 실행 벡터(create/edit)** 를 모두 단일 source 로 묶어 12-way 를 완성했다.

step④ 멱등 chain 은 두 개의 gh CLI 인자-벡터를 거친다: **(1) first-step search 벡터(`searchArgv`)** — live runner 가 `execFile('gh', searchArgv)` 로 `gh search issues` 를 호출해 hit 을 얻는다. **(2) second-step create/edit 벡터(`resolvePlan.argv`)** — search 결과에 따라 `gh issue create` 또는 `gh issue edit` 를 호출한다. T-0781 은 (2) resolve-argv 의 위치-정합을 closure 에 합류시켰다. 그러나 **(1) searchArgv 의 전체-벡터 위치-정합(동사 prefix·`--match body` 고정·`--json` 필드 상수·`--limit` 값 상수 의 위치별 byte-identical)** 은 아직 convergence closure 에 미합류된 distinct 표면이다.

`searchArgv` 전체-벡터 위치-정합 축은 resolve-argv 벡터(T-0781) 및 command-args 객체 surface(T-0778~0780)와 distinct 한 표면이다:

- **search-argv 전체-벡터 위치-정합 축(본 task 의 새 표면)** — `stepArgs.publish.searchArgv: string[]` 는 `buildRealDataResultIssueSearchGhArgv(commandArgs)`(`realdata-e2e-result-issue-search-argv.ts`, T-0586)가 산출한 canonical 벡터다:
  - `searchArgv == ["search", "issues", "--match", "body", searchQuery, "--json", "number,title,body", "--limit", "30"]`(search-argv 122~132행). 즉 `searchArgv[0]=="search"`, `searchArgv[1]=="issues"`, `searchArgv[2]=="--match"`, `searchArgv[3]=="body"`, `searchArgv[4]==commandArgs.searchQuery`(=descriptor.marker), `searchArgv[5]=="--json"`, `searchArgv[6]=="number,title,body"`(=`REAL_DATA_RESULT_ISSUE_SEARCH_JSON_FIELDS`), `searchArgv[7]=="--limit"`, `searchArgv[8]=="30"`(=`REAL_DATA_RESULT_ISSUE_SEARCH_LIMIT`).
  - 이 searchArgv 전체-벡터는 closed command-args surface(`commandArgs.searchQuery`)의 단일-source marker 토큰을 **`--match body` 다음 위치(index 4)** 로 운반하고, 나머지 위치(동사 prefix·`--json` 필드·`--limit` 값)는 **입력-비종속 결정론 상수**로 고정한다. resolve-argv(T-0781)는 create/edit second-step 벡터였고 searchArgv 는 그 앞 first-step search 벡터 — distinct surface. 이 "searchArgv 전체-벡터의 위치별 값이 단일-source command-args(searchQuery=marker) + 결정론 상수로 byte-identical 조립됨" 정합은 aggregator+resolve+post closure 에 미합류.

직전 sibling 들은 이 search-argv 전체-벡터 위치-정합 축을 convergence closure 에 합류시키지 않았다:
- **T-0781 (aggregator 12-way)**: `resolvePlan.argv`(second-step create/edit 벡터)의 위치-정합을 합류 박제. searchArgv(first-step)는 등장하나 marker 토큰(`--match body` 다음)만 소비 — 전체-벡터 위치-정합 미합류.
- **T-0775/0774/0773 (aggregator 6·5·4-way)**: `stepArgs.publish.searchArgv` 를 합류 축으로 잡았으나, 그 안 searchArgv 사용은 모두 `extractSearchMarker(searchArgv) = searchArgv[searchArgv.indexOf("--match")+2]` 의 **`--match` 마커 토큰만** 추출(각 spec 124~132·137~147·118~130행). 4-way 690행은 두 chain 의 searchArgv 간 `toEqual`(결정론 deep-equal)일 뿐 **canonical 전체-벡터(`["search","issues","--match","body",marker,"--json","number,title,body","--limit","30"]`) 와의 byte-identical toEqual·위치별 동사/--json/--limit 상수 단언 0**.
- **search-argv self-guard**: `assertRealDataResultIssueSearchGhArgvPreservesCommandArgs`(T-0655, search-argv 142~145행) + `assertRealDataResultIssueSearchJsonFieldsMatchParseShape`(T-0657, 157~160행)가 빌더 내부 self-wire 로 round-trip 을 박제했으나 **aggregator(`buildRealDataE2eStepArgs`) 진입·resolve·post 미합류**(빌더 단독 self-guard).

본 task 는 그 빈 자리를 채워 **publish leg 의 searchArgv 가 first-step gh search 인자-벡터를 전체-위치-정합(동사 prefix·`--match body`·searchQuery=marker·`--json` 필드 상수·`--limit` 값 상수)으로 조립함을 같은 aggregator 산출 + resolve-argv(second-step) + descriptor 재유도와 묶어 closure 에 합류**시킨다. 단일 source `(runPlan, activities, results, search-stdout, exec-stdout)` 로부터:

1. **search-argv 전체-벡터 위치-정합(축 13, 본 task 의 새 표면)** — `stepArgs = buildRealDataE2eStepArgs(runPlan, activities, results)` → `stepArgs.publish.searchArgv` 가 **byte-identical deep-equal**(`toEqual`) `["search","issues","--match","body",stepArgs.publish.commandArgs.searchQuery,"--json","number,title,body","--limit","30"]`(원소·순서·길이). 특히 `searchArgv[4]==commandArgs.searchQuery`(=descriptor.marker, 단일-source marker 운반), 나머지 8 위치는 결정론 상수.
2. **resolve-argv update/create 위치-정합(축 12, 12-way 묶음 항)** — search hit N → `resolvePlan.argv == ["issue","edit",String(N),"--title",updateArgs.title,"--body",updateArgs.body]`, search hit 0 → `["issue","create","--title",createArgs.title,"--body",createArgs.body,"--label","realdata-e2e","--label","result"]`.
3. **publish-leg command-args-labels 고정-상수 일치(축 11)** — `commandArgs.createArgs.labels` 가 `["realdata-e2e","result"]` deep-equal.
4. **publish-leg command-args-title/body 두 경로 일치(축 9~10)** — `createArgs/updateArgs.title` 가 `descriptor.title`, `createArgs/updateArgs.body` 가 `descriptor.body` 와 byte-identical.
5. **publish-leg descriptor-{title,body}·summary 재유도(축 6~8)** — `descriptor.{title,body}`·`report.summary` 가 `buildRealDataResultIssueCommandPlan(results, runPlan.run).report.{descriptor.{title,body},summary}` 와 byte-identical.
6. **evaluation-leg inputs 재유도 + 페어링 + modelId thread(축 4~5)** — `evaluation.inputs == buildRealDataEvaluationInputs(activities)`, `callArgs[i].input === inputs[i]`, `callArgs[i].options.modelId === runPlan.pipeline.modelId`.
7. **publish-leg marker 3-축 일치(축 2~3)** — `descriptor.marker === commandArgs.searchQuery === searchArgv[4]`(이번 task 에서 `--match` 다음 위치를 전체-벡터의 index 4 로 명시 박제).
8. **resolve issueNumber + post run-identity(축 1, 종단)** — `resolvePlan.action.update.issueNumber = N` → `outcomeReport = buildRealDataResultOutcomeStepArgs(runPlan, execStdout)` → `{issueNumber, gitSha, dateToken, ...}` 가 동일 runPlan.run 전파.

이 13-way(search-argv 전체-벡터 위치-정합 + resolve-argv update/create 위치-정합 + command-args labels 고정상수 + command-args title/body 두 경로 + descriptor.{title,body} 재유도 + summary 재유도 + inputs 재유도 + modelId + marker 3-축 + resolve issueNumber + post run-identity)가 **세 검증 source `(runPlan, activities, results)`** single-source 로 수렴함이 **search-or-update 멱등성**(REQ-009 — 같은 단일-source marker 가 first-step search 벡터의 정확한 위치로 운반되고 그 검색 결과가 create/edit argv 로 동형 조립)·**raw 미보유 평가 입력/결과 집계 정합**(REQ-032)·**결과 리포트 재실행 정합**(REQ-037)의 aggregator-level "first-step search 인자-벡터가 전체-위치 byte-identical 조립됨(marker 운반 + 결정론 상수)이 같은 세 검증 source 의 산물" 의 종단 닫음이다. **step④ 멱등 chain 의 두 gh CLI 벡터(first-step search + second-step create/edit)가 모두 단일-source 로 전체-위치 묶이는 slice** 다.

gap 확인(git grep, origin/main 62a4de1f): aggregator+searchArgv 참조 smoke 는 **3파일(4·5·6-way)** 이나 그 안 searchArgv 사용은 모두 `extractSearchMarker(searchArgv) = searchArgv[indexOf("--match")+2]` 의 **`--match` 마커 토큰만** 추출. 4-way 690행은 두 chain searchArgv 간 결정론 deep-equal 일 뿐 **canonical 전체-벡터(`["search","issues","--match","body",marker,"--json","number,title,body","--limit","30"]`) 와의 byte-identical toEqual·동사/--json/--limit 위치별 상수 단언 0**. `aggregator-*search-argv-positional* smoke 파일 부재` + `git log origin/main` 동일 영역 박제 commit 0.

live leg(실 prisma·실 collectForPerson·실 github.com fetch·실 LLM scoring·실 gh CLI 실행·DB·LAN gate) 복제 0·non-gated 항상 실행 — 순수 build-time in-memory 검증만.
