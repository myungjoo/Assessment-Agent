# T-0935 — realdata-e2e dual-leg run report create-branch output-parse issueNumber genesis execute-side single-source closure non-gated smoke

## Why

PLAN.md 109행 (🟢 실 평가 e2e, P5) step④ (daily-test dual-leg run 결과 rolling-issue 멱등 박제) chain 의 **create 분기 실행-후(execute-side) output-parse — 갓 생성된 이슈 번호가 태어나는 지점(genesis)** 이 아직 어떤 smoke 에도 chain 그물로 묶이지 않았다. step④ 의 rolling-issue 는 검색으로 기존 이슈를 못 찾으면(빈 search) `gh issue create` 로 새 이슈를 만들고, 그 명령의 stdout(갓 생성된 이슈 URL)을 파싱해 **새로 태어난 이슈 번호 M** 을 확인한다.

이 create-branch 의 execute-side 는 update-branch(T-0920)와 **issueNumber 의 출처가 정반대**다:

- **update 분기(T-0920 이 봉합)** — 기존 이슈 번호 N 은 **실행 이전**에 이미 존재한다: search-hit stdout 의 최소 number N → resolve action `{action:"update", issueNumber:N}` → `plan.argv[2] === String(N)`(실 `gh issue edit N` argv 원소) → 실행 후 output-parse `outcome.issueNumber === N`. N 은 **pre-exec 3+지점 + post-exec 1지점** 을 관통한다.
- **create 분기(본 task 가 봉합)** — 갓 생성될 이슈 번호 M 은 **실행 이전 어디에도 없다**: 빈 search(`"[]"`) → resolve action `{action:"create"}`(issueNumber 필드 자체 부재 — T-0933 이 pre-exec 부재를 봉합) → `plan.argv = ["issue","create","--title",...,"--body",...,...labels]`(M 원소 전무 — 아직 이슈가 없어 번호를 알 수 없다) → **실행 후에야** `gh issue create` stdout 의 URL `https://github.com/owner/repo/issues/M` 에서 **output-parse 가 M 을 처음으로 산출**한다. M 은 **pre-exec 0지점 + post-exec 1지점**, 즉 output-parse 에서 **태어난다(genesis)**.

이 비대칭이 rolling-issue 멱등의 execute-side 두 반쪽이다: 첫 밤(create)은 이슈를 새로 만들며 그 번호가 output-parse 에서 태어나고, 다음 밤(update)은 그 이슈를 marker 로 검색해 찾은 번호로 갱신한다(REQ-009 — 동일 run 의 이슈를 다음 밤 검색이 찾아 재갱신). 만약 create output-parse 가 손상 stdout 에서 조용히 잘못된 M 을 산출하면 — live wiring 이 그 M 을 다음 밤의 검색·추적 기준으로 삼아 rolling-issue 멱등이 첫 밤부터 어긋난다. 반대로 M 이 pre-exec create argv 로 새면(silent leak) — 아직 존재하지 않는 번호로 `gh issue create` 를 호출해 명령이 실패한다.

그러나 이 **create-branch output-parse issueNumber genesis single-source closure** 를 어느 smoke 도 chain 그물로 검증하지 않는다:

- 형제 T-0920(edit-argv issueNumber execute-side closure)은 **update 분기**에서 기존 이슈 번호 N 이 search-hit → resolve → `plan.argv[2]` → output-parse 4지점 수렴함만 자산화한다 — 본 task 는 그 **정확한 거울상**(create 분기, 번호가 pre-exec 어디에도 없다가 output-parse 에서 태어남).
- 형제 T-0933(update-branch issueNumber single-source + create-absence orthogonal)은 create 분기 plan.argv 및 action 에 issueNumber 원소·필드가 **전무**함(pre-exec 부재)만 자산화한다 — 그러나 그 다음 실행-후 output-parse 가 create stdout URL 에서 M 을 **새로 산출**함(genesis)은 미단언(pre-exec 부재만, post-exec genesis 는 다른 축).
- 형제 T-0918(descriptor→resolve→output-parse triple-boundary)은 **update 분기** resolve↔output-parse issueNumber 수렴(action.update.issueNumber == outcome.issueNumber)만 자산화한다 — create 분기의 output-parse 는 대조 대상 아님(update 분기 내부).
- 형제 T-0934(action-verb dispatch)은 create/update **분기 선택 판단**(argv[1]=create/edit)만 자산화한다 — 실행 후 output-parse 는 dispatch 이후 별개 축.

본 task 는 그 **create-branch output-parse genesis seam** 을 닫는다 — T-0920(edit-side) 의 거울상 sibling. chain: 두 leg outcome + run → report → descriptor → commandArgs 를 통과시켜 유효 commandArgs 를 얻고, 빈 search(`"[]"`)에 종단 컴포저를 적용해 create plan 을 산출한 뒤(create action 에 issueNumber 필드 부재·create plan.argv 에 M 원소 전무 확인), **create execStdout(`gh issue create` 가 낸 갓 생성 이슈 URL `.../issues/M`)** 을 output-parse 로 파싱해 `outcome.issueNumber === M` 이 오직 그 execStdout URL 에서만 유도되고 실행 이전 create chain 어디에도 M 이 없음을 박제한다.

issue-still-relevant 확인(2026-07-12): `ls test/smoke | grep dual-leg | grep -iE "create-branch.*output-parse|output-parse.*create|create.*genesis|create.*execute-side"` = **0개**(create-branch execute-side output-parse genesis seam 미봉합 — output-parse execute-side 는 T-0920 edit-side 뿐, create-side 부재). `git log origin/main` 동일 영역(dual-leg create-branch output-parse genesis smoke) 박제 commit 0 — T-0747(#662)은 summary 축의 `create-edit-output→outcome-report` 로 dual-leg 축·create/update 비대칭 genesis 와 무관(다른 파일). output-parse 파서(`parseRealDataDailyStepDualLegRunReportIssueCreateEditOutput`, T-0903)·create argv 빌더(T-0899)·종단 컴포저(T-0902) 배선은 이미 main 에 박제됨 — 본 task 는 그 배선을 **다시 만들지 않고** create-branch output-parse genesis 를 대조하는 **smoke 그물만** 신설.
