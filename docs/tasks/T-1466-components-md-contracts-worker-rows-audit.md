# T-1466 — components.md `## Contracts` Worker 발신 4 row 대조

## Why

[T-1465](T-1465-components-md-contracts-scheduler-rows-audit.md) 가 `## Contracts` 표의 **Scheduler 발신 2 row (278 · 279 행)** 를 닫으면서 ([REQ-COVERAGE-AUDIT.md](../use-cases/REQ-COVERAGE-AUDIT.md) `§ 12.63`) 파생 영향 **(1)** 에서 **다음 slice 1 순위를 잔여 8 row 중 `Worker` 발신 4 row (280 ~ 283 행)** 로 명시 지목했다 (근거: 대응 mermaid edge **4** 개 (**80 ~ 83** 행) 를 `§ 12.56` 이 이미 닫아 **판정 입력이 그대로 재사용** 되므로 한계 비용 최저). 본 slice 는 그 지목을 그대로 승계한다.

동시에 `§ 12.56` 은 자기 각주 말미 (components.md **203** 행) 에서 **"대응 `## Contracts` row 4 개 (280 ~ 283 행) 는 edge 4 개와 1:1 대응하나 그 판정은 파생 영향 (3) 소관"** 이라고 **명시 이월** 해 뒀다. 본 slice 는 그 이월을 회수하는 slice 이기도 하다 — `§ 12.62` 가 `§ 12.55` 의 이월을, `§ 12.63` 이 `§ 12.54` 의 이월을 회수한 것과 **동형** 이다. 따라서 **`worker` node 외연 (= `src/assessment-collection/` + `src/assessment-evaluation/` 2 디렉토리)** 도 `§ 12.55` · `§ 12.56` **승계 + 유효성 재검증** 이며 본 절 신설이 아니다.

planner 사전 확인 — **아래는 전부 가설이며 전제가 아니다** (T-1440 AC 1 이후 planner 기대가 실측에 반증·정정된 선례가 **27** 회 있고, 직전 T-1465 에서도 "`§ 12.54` 가 박제한 `@Cron` 6 지점 중 뒤 2 개가 stale 일 것" 이라는 기대가 **stale 0** 으로 **반증** 됐다 — T-1461 이 이미 in-place 정정해 뒀기 때문이다). executor 는 AC 1 에서 전부 재측정하고 **기대와 다르면 그 축의 판정을 실측대로 뒤집는다**. ① **280** 행 `Worker | GitHub Adapter | sync | TypeScript method call (in-process) | 평가 파이프라인의 commit/Issue fetch path.` 의 **결선 실재 + 비고의 `commit/Issue fetch path`** — `§ 12.56` 이 edge 80 을 **참** (실 hit **4** — `github-collection.service.ts` **29 · 71** 행 · `github-org-repo-enumerate.service.ts` **20 · 28** 행) 으로 닫았으므로 결선 축은 승계 가능성이 크나, **비고의 `commit/Issue fetch path` 어휘가 실 호출 대상 (commit? issue? repo enumerate?) 과 맞는지** 는 edge label 이 다루지 않은 **새 축** 이다. ② **281** 행 (`Worker | Confluence Adapter | … | 평가 파이프라인의 page fetch path.`) — `§ 12.56` edge 81 **참** (hit **2** — `confluence-collection.service.ts` **37 · 54** 행) 승계 가능성 + 비고의 `page fetch path` 어휘 정합. ③ **282** 행 (`Worker | LLM Gateway | sync (await) | … | 평가문 생성 / 난이도 분류 호출. provider 별 latency 가 다양하므로 concurrency limit 동반 (ADR-0003 §1).`) — edge 82 **참** (hit **8**) 승계 가능성 + **`concurrency limit 동반` claim 의 코드 실재 여부** (본 slice 의 가장 값비싼 새 축 — `p-limit` · semaphore · `Promise.all` 상한 · batch size 상수 중 무엇도 없으면 **거짓**) + **`난이도 분류` 가 LLM 호출인지 규칙 기반인지**. ④ **283** 행 (`Worker | DB Persistence | sync | Prisma typed query (in-process) | 평가 결과 저장. raw 저장 금지 (REQ-032) — schema 가 raw column 미정의.`) — `§ 12.56` 이 edge 83 을 **부분참** (`src/assessment-evaluation/` 만 `PrismaService` 직접 주입 **4** code line, `src/assessment-collection/` 은 Prisma 의존 **0**) 으로 닫았으므로 row 도 같은 **부분참** 승계 가능성. ⑤ 283 행 비고의 **`raw 저장 금지 (REQ-032) — schema 가 raw column 미정의`** — components.md **149** 행 각주가 이미 **schema 15 model 전수로 참** (raw 본문 컬럼 **0**) 임을 박제했으므로 **재판정이 아니라 1 구 인용 승계** 이며, 본 축이 새로 가르는 것은 **그 claim 이 `Worker → DB` contract 셀에 놓일 자리인가 (= 계약 표기인가 schema 정책인가)** 뿐이다. ⑥ 4 row 의 `sync/async` 값 — **282** 행만 **`sync (await)`** 라는 **괄호 한정** 이 붙은 비대칭 ↔ **289** 행 정의문 (`§ 12.62` 가 **in-process 판별력 0**, `§ 12.63` 이 **괄호 한정 비대칭** 을 확정) 의 **3 회째 증상** 인지. ⑦ 비고 셀 **pointer 분포** — 282 행만 ADR pointer (`ADR-0003 §1`) · 283 행만 REQ pointer (`REQ-032`) 이고 **280 · 281 행은 pointer 0** 인 불균일 + 그 pointer 대상의 실재 (ADR-0003 **34** 행 `Decision §1` · requirements.md `REQ-032` row). REQ 컬럼 부재가 결손이 아니라는 판정은 `§ 12.62` 축 ⑦ · `§ 12.63` 축 ⑦ **승계이며 재판정 아님**. ⑧ **message format 셀의 판별력** — `TypeScript method call (in-process)` 문자열이 **274 ~ 276 · 280 ~ 281** 등 여러 row 에 · `Prisma typed query (in-process)` 가 **273 · 283** 2 row 에 공유돼 셀이 **발신 · 수신 쌍을 구별하지 못하는지** (`§ 12.62` 축 ⑥ 의 `sync` 판별력 0 과 **같은 병리의 다른 컬럼** 면).
