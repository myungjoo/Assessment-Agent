# T-1088 — github-collection-live plan 구조-검사 선행성 order-lock (clean leg — 신규 namespace import + spyOn 인프라)

## Why

P5 test-hardening 의 realdata-e2e 구조-guard 선행성 sweep(T-1065 §D 후보 (a))은 descriptor-body 축(T-1085/T-1086)·step-args 축(T-1082~T-1084)·evaluation-inputs producer 축(T-1087)을 소진했다. T-1087 Follow-up 이 leg 23 후보로 지목한 **imported value 재유도 delegate 를 호출하는 잔여 producer/aggregator 축**을 grep 실증으로 재감사한 결과, `github-collection-live plan consistency 가드`(`test/helpers/realdata-e2e-github-collection-live-consistency.ts`)가 **imported value delegate `resolveGithubApiBaseUrl` 를 요소별로 재유도 호출**하면서 재유도-앞 구조 error-path 에 delegate 0-call spy 가 결손된 적격 축으로 확인됐다. 이 가드 `assertRealDataGithubCollectionPlanConsistent`(L309~)는 실 GitHub 수집 e2e 체인 step ①(collection)에서 gating + seeds 로부터 산출한 수집 plan 이, 동일 source 를 독립 재유도(`deriveExpectedPlan` L321 → `seeds.map((seed)=>({..., apiBaseUrl: resolveGithubApiBaseUrl("github.com"), ...}))` L200~207)한 expected 와 조립 필드(enabled + entries 길이 + 각 슬롯)에서 정합함을 대조하는 post-derivation 무결성 가드다(README.md 109행 step ① 수집 plan chain / REQ-032·REQ-059). 재유도 delegate 는 **1개**(`resolveGithubApiBaseUrl`, `src/github/github-request.builder`), 재유도보다 앞서는 error 범주는 **1종**(gating/seeds/plan 구조 TypeError — 3 guard × 총 6 분기).

**clean-leg 성격(variant 아님)**: 본 leg 의 spec(총 560줄)은 delegate `resolveGithubApiBaseUrl` 를 **아예 import 하지 않으며**, `import * as` namespace import 도 `jest.spyOn` 도 `toHaveBeenCalled*` 도 전무하다(pre-check grep: `resolveGithubApiBaseUrl` = spec 미참조, `toHaveBeenCalledTimes` = 0, `jest.spyOn` = 0, `import * as` = 0). 따라서 본 leg 는 T-1085/T-1086/T-1087 과 같은 **clean-leg** — delegate 의 **신규 namespace import 신설 + spyOn 인프라 신설**이 필요하다.

planner pre-check(실 grep + read, 2026-07-18, HEAD c6488188 = T-1087 머지 포함)로 확인한 gap: 이 가드는 본문에서 **상위 구조 assert 3개**(`assertGatingStructure(gating, label)` L316 — gating 비-객체 → TypeError / `assertSeedsStructure(seeds, label)` L317 — seeds 비-배열 → TypeError / `assertPlanStructure(plan, label)` L318 — plan 비-객체/enabled 비-boolean/entries 비-배열 → TypeError) **셋 모두를** 요소별 재유도 위임(`deriveExpectedPlan` L321 내 `seeds.map` → `resolveGithubApiBaseUrl` L207)보다 **먼저** 수행한다(구조검사 L316~318 < 재유도 L321). 구조 검사와 재유도 **사이에 RangeError 분기가 없다** — 값 정합 위반 RangeError(enabled drift L324 / entries 길이 L331 / 슬롯 drift L338~ / byte-identical L350)는 전부 재유도 **뒤**에 온다. 그러나 대응 spec 의 구조 error-path describe(`error path — plan 구조 결손 → TypeError` L202~: plan null L203·비객체 L213·enabled 비-boolean L223·entries 비-배열 L237 / gating null L251 / seeds 비배열 L265)는 `.toThrow(...)` 만 assert 하고 delegate 호출 횟수를 못박지 않는다. 즉 **재유도-앞 error 입력(구조 결손)을 주면 mapper delegate 가 `toHaveBeenCalledTimes(0)` 이어야 한다는 선행성**이 spy 로 못박혀 있지 않다. 이를 재유도-앞 6 분기에 delegate `resolveGithubApiBaseUrl` `toHaveBeenCalledTimes(0)` 으로 못박아 "gating/seeds/plan 구조 검사 → 요소별 재유도" 순서를 silent 재정렬로부터 방어한다(T-1066~T-1087 와 동형 defense-in-depth, delegate 1개, error 범주 1종). test-only 1파일, production `src`·helper `.ts` 로직 무변경.

**0-call 범위 경계(중요, per-seed map + early-return 특이점)**: 본 leg 의 0-call 선행성은 **재유도(L321)보다 앞서는 상위 구조 error 범주**에만 적용한다 — gating 비-객체, seeds 비-배열, plan 비-객체/enabled 비-boolean/entries 비-배열 (6 분기 모두 delegate 호출 **이전**에 throw → delegate `toHaveBeenCalledTimes(0)`). **재유도 delegate 는 per-seed map 호출**이므로 정상 도달 경로에서 호출 횟수는 **`seeds.length`(1 아님)**임에 유의한다 — 단 `deriveExpectedPlan` 은 `gating.enabled !== true` 시 early-return(L192~193)하여 seed 를 읽지 않으므로 **gating.enabled === true 일 때만** delegate 가 `seeds.length` 회 호출되고, gating disabled happy-path 는 **0-call**(seed map 미실행). 따라서 happy-path spy N-call 재확인은 **gating.enabled=true + seeds.length ≥ 1** fixture 로 수행한다. 값 정합 위반 RangeError(enabled/entries 길이/슬롯 drift, 재유도 뒤)도 gating enabled fixture 면 delegate 가 `seeds.length` 회 호출되므로 `toHaveBeenCalledTimes(seeds.length)`(> 0). 이 N-call+early-return 특이점이 검증 포인트다. **out-of-scope**: 개별 seed 원소의 구조 결손(github.com identity 부재/빈 externalId 등)으로 `deriveExpectedUsername`(L143~)가 map **도중** throw 하는 경우 — 해당 seed 앞의 seed 들에 대해 `resolveGithubApiBaseUrl` 가 이미 호출됐을 수 있어(call-then-throw) 0-call 범위 밖(별도 seed-level mid-map defect domain).
