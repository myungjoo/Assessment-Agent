# T-0786 — realdata-e2e step④ aggregator evaluation-leg callArgs[i].input 내부-shape 1:1 thread 합류 17-way single-source closure non-gated build-time smoke 신설

## Why

PLAN.md §109(🟢 실 평가 e2e, P5)의 build-time 순수 layer 는 최외곽 단일 진입 `buildRealDataE2eRunPlan(seeds, modelId, run)` → `{pipeline, run}`(T-0597)을 산출하고, 그 `runPlan` 을 pre-실행 aggregator `buildRealDataE2eStepArgs(runPlan, activities, results)` → `{evaluation, publish}`(T-0601)에 통째로 넘긴다. 직전 sweep(T-0778~0785)은 aggregator 산출의 evaluation-leg + publish-leg + collect-leg **표면 + collect-leg 내부-shape**(serviceIdentities 배열 깊이, T-0785)를 단일 source 로 묶어 16-way 를 완성했다. 특히 evaluation-leg 의 inputs 축은 T-0571(aggregator 6-way)/7-way 가 `stepArgs.evaluation.inputs == buildRealDataEvaluationInputs(activities)` **top-level deep-equal** + `callArgs[i].input === inputs[i]` reference 페어링으로 합류시켰다.

그러나 evaluation-leg 의 **input 내부-shape 깊이**(Activity → EvaluationInput 필드 차원)에는 16-way 가 닫지 않은 seam 이 남아있다 — aggregator 가 산출한 `stepArgs.evaluation.inputs[i]`(= `callArgs[i].input`, type `EvaluationInput`)의 각 필드(`unitId`·`contributionKind`·`sourceType`·`instanceKey`·`author`·`timestamp`·`metadata`)가, 검증 source `activities[i]`(type `Activity`)로부터 production 단건 매퍼 `mapActivityToEvaluationInput(activities[i])` 와 **필드별 byte-identical 1:1**(특히 `unitId = ${sourceType}:${instanceKey}:${externalId}` 합성, `contributionKind` 의 R-30 routing — github issue→document·commit/pr→code·confluence→document, `metadata` reference 승계, raw 본문 key 부재)임은 aggregator+resolve 종단 closure 에 미합류다.

evaluation-leg input 내부-shape 축은 16-way 가 잡은 16축과 distinct 한 표면이다:

- **evaluation-leg input 내부-shape 1:1 thread 축(본 task 의 새 표면)** — aggregator 가 `buildRealDataE2eStepArgs` 위임 `buildRealDataEvaluationStepArgs`(T-0598) 경유 `buildRealDataEvaluationInputs(activities)`(T-0578) → 각 원소 `mapActivityToEvaluationInput(activity)`(production 매퍼) 로 산출한 `stepArgs.evaluation.inputs[i]` 가:
  - `mapActivityToEvaluationInput(activities[i])` 와 **필드별 byte-identical**(`unitId`·`contributionKind`·`sourceType`·`instanceKey`·`author`·`timestamp` 동일, `metadata` 는 동일 reference).
  - `unitId === ${activities[i].sourceType}:${activities[i].instanceKey}:${activities[i].externalId}`(합성 규칙 재유도 — 본 task 는 production 매퍼 산출과의 byte-identical 만 단언, 합성 로직 자체 재구현 0).
  - `contributionKind` 의 **R-30 routing 모든 분기**: github `commit`→`code`, github `pr`→`code`, github `issue`→`document`(R-30 — issue 를 문서 기여로), confluence→`document`.
  - `metadata` 가 입력 `activities[i].metadata` 와 **동일 reference**(매퍼 계약 — deep clone 0).
  - **raw-not-stored boundary**(REQ-032) — `inputs[i]` 의 key set 이 `{unitId, contributionKind, sourceType, instanceKey, author, timestamp, metadata}` 와 set-equal, commit message 전문·diff·page 본문·issue body 같은 raw 본문 key 부재.
  - 이 1:1 이 aggregator 가 publish 로 thread 하는 **그 동일 `runPlan` 의 evaluation-leg** 에서 나온다(`callArgs[i].input === inputs[i]` reference, 16-way 묶음 항).

직전 sibling 들은 이 input 내부-shape 1:1 축을 aggregator convergence closure 에 합류시키지 않았다:
- **T-0785 (aggregator 16-way)**: collect-leg serviceIdentities 내부-shape 1:1 + collectCallArgs top-level 재유도 + 14축을 묶었으나 **evaluation-leg input 내부의 필드 깊이는 미합류**(evaluation.inputs 자체를 top-level deep-equal·페어링 묶음으로만 다룸).
- **T-0571 (aggregator 6-way) / 7-way**: `stepArgs.evaluation.inputs == buildRealDataEvaluationInputs(activities)` top-level deep-equal(`toEqual`) + `callArgs[i].input === inputs[i]` reference 페어링 + `typeof inputs[0].unitId === "string"`·`length > 0`·`typeof inputs[0].contributionKind`(316~318·387행, **첫/일부 원소 sanity 만**) — `inputs[i]` 의 필드별 `mapActivityToEvaluationInput(activities[i])` 재유도(github 3분기+confluence)·`metadata` reference·raw key 부재 boundary 단언 0.
- **T-0775~0784 (aggregator 4~15-way)**: evaluation-leg input 내부-shape 미합류 또는 collect/search/resolve/descriptor 축만 — input 필드 깊이 1:1 합류 0.
- **evaluation-inputs helper spec / production mapper spec**: `buildRealDataEvaluationInputs`(T-0578) + `mapActivityToEvaluationInput`(evaluation-input.mapper.ts) self-guard·spec 가 unitId 합성·contributionKind routing·raw 미보유를 박제했으나 **aggregator(`buildRealDataE2eStepArgs`) chain 진입·resolve·post 미합류**(매퍼/빌더 단독 spec — aggregator 산출 inputs 의 내부-shape ↔ activities 1:1 종단 정합 0).

본 task 는 그 빈 자리를 채워 **aggregator 가 산출한 evaluation-leg inputs[i](=callArgs[i].input)가 검증 source activities[i] 로부터 production mapActivityToEvaluationInput 와 필드별 byte-identical 1:1(github commit/pr/issue·confluence 모든 분기, metadata reference, raw key 부재) 임을, inputs top-level 재유도·callArgs.input 페어링·collect-leg·publish-leg·resolve·post 와 묶어 closure 에 합류**시킨다. 단일 source `(seeds, modelId, run, activities, results, search-stdout, exec-stdout)` 로부터:

1. **evaluation-leg input 내부-shape 1:1 thread(축 17, 본 task 의 새 표면)** — `stepArgs = buildRealDataE2eStepArgs(runPlan, activities, results)` → 모든 i 에 대해 `stepArgs.evaluation.inputs[i]` 가 `mapActivityToEvaluationInput(activities[i])` 와 필드별 byte-identical(`toEqual`), `unitId`·`contributionKind`·`sourceType`·`instanceKey`·`author`·`timestamp` 각 `toBe`, `metadata` 동일 reference(`toBe`), key set == `{unitId,contributionKind,sourceType,instanceKey,author,timestamp,metadata}` set-equal(raw key 부재). github commit/pr/issue·confluence 4분기 활동 모두 합성해 contributionKind routing 단언.
2. **evaluation-leg inputs top-level 재유도 + callArgs.input 페어링(축 6, 6-way 묶음 항)** — `stepArgs.evaluation.inputs` 가 byte-identical deep-equal `buildRealDataEvaluationInputs(activities)`, 모든 `callArgs[i].input === inputs[i]`(reference), 길이 == activities.length.

4. **collect-leg call-args top-level 재유도(묶음 항)** — `runPlan.pipeline.collectCallArgs == buildRealDataCollectCallArgs(seeds)`, since/assessmentId placeholder.
5. **search-json-fields↔parse-shape set-equal + number thread(묶음 항)** — `searchArgv[6]` split 집합 == `REAL_DATA_RESULT_ISSUE_SEARCH_PARSE_SHAPE_KEYS` == 실 파싱 hit 키 set-equal, number N → resolve → post.
6. **collect/evaluate modelId 공유(묶음 항)** — `runPlan.pipeline.modelId === modelId === callArgs[i].options.modelId`.
7. **search-argv 전체-벡터 + resolve-argv create/update(묶음 항)**.
8. **publish-leg command-args-labels + title/body 두 경로 + descriptor·summary 재유도(묶음 항)**.
9. **marker 3-축 + resolve issueNumber + post run-identity(종단)**.

이 17-way(evaluation-leg input 내부-shape 1:1 + inputs top-level 재유도 + callArgs.input 페어링 + collect-leg serviceIdentities 내부-shape + collectCallArgs top-level 재유도 + collect/evaluate modelId 공유 + search-json-fields↔parse-shape set-equal + number thread + search-argv 전체-벡터 + resolve-argv create/update + command-args labels + title/body 두 경로 + descriptor 재유도 + summary + marker 3-축 + resolve issueNumber + post run-identity)가 **검증 source `(seeds, modelId, run, activities, results)`** single-source 로 수렴함이 **search-or-update 멱등성**(REQ-009)·**Issue 를 문서 기여로 평가하는 정규화 정합**(REQ-030/R-30)·**raw 미보유 평가 입력 정합**(REQ-032)·**author 귀속 key 정합**(REQ-047)의 aggregator-level "aggregator 가 step③ scoreUnit 로 넘길 평가 입력 1건의 필드(unitId 식별자·contributionKind category·author 귀속·timestamp)가 검증 source activity 와 필드별 어긋남 0, raw 본문은 입력으로 새지 않음" 의 종단 닫음이다. **e2e 의 evaluation-leg 가 검증 source activity 의 Activity→EvaluationInput 필드 깊이까지 단일 검증 source 에서 1:1 로 맞물리는 seam slice** 다.

- [ ] **Happy-path aggregator 17-way chain 합성**: 단일 source — `seeds: RealDataSeedDescriptor[]`(여러 Person) + 임의 양수 `modelId`(비-empty) + `run: {gitSha, dateToken}`(비-empty) + `activities: Activity[]`(**github commit·github pr·github issue·confluence page 4종 모두 1+ 원소 포함**, 다양한 instanceKey/author/timestamp/metadata) + `results: EvaluationResult[]`(여러 원소) synthetic literal, 임의 양수 `N`. 다음을 한 chain 으로 호출: `runPlan = buildRealDataE2eRunPlan(seeds, modelId, run)` → `stepArgs = buildRealDataE2eStepArgs(runPlan, activities, results)` → `searchStdout`(N 담은 hit JSON 배열) → `parsedHits = parseRealDataResultIssueSearchOutput(searchStdout)`(1+ hit) → `resolvePlan = resolveRealDataResultIssueGhCommandPlan(searchStdout, stepArgs.publish.commandArgs)`(update 분기) → `execStdout`(`/issues/N` URL) → `outcomeReport = buildRealDataResultOutcomeStepArgs(runPlan, execStdout)`. 산출물 모두 정상(stepArgs.evaluation.inputs 비어있지 않은 배열·길이==activities.length, callArgs 동일 길이, parsedHits·resolvePlan·outcomeReport 정상) happy test 1+.
- [ ] **evaluation-leg input 필드별 1:1 재유도 수렴(branch — 핵심 불변식, 본 task 의 새 표면)**: 모든 i 에 대해 `stepArgs.evaluation.inputs[i]` 가 `mapActivityToEvaluationInput(activities[i])`(production 매퍼 직접 호출) 와 byte-identical deep-equal(`toEqual`) 임을 단언 1+ test. 추가로 필드별: `inputs[i].unitId === mapped.unitId`(`toBe`, 그리고 `=== ${activities[i].sourceType}:${activities[i].instanceKey}:${activities[i].externalId}`), `inputs[i].contributionKind === mapped.contributionKind`, `inputs[i].sourceType === activities[i].sourceType`, `inputs[i].instanceKey === activities[i].instanceKey`, `inputs[i].author === activities[i].author`, `inputs[i].timestamp === activities[i].timestamp`(모두 `toBe`, forEach). **단언 shape·필드명은 production 매퍼(evaluation-input.mapper.ts) 및 `EvaluationInput`(evaluation-input.ts 56행) 시그니처로 확인해 정확히 박제** — 형식이 다르면 production 기준으로 조정(본문에 사유 명시).
