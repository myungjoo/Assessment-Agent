# T-0794 — deploy step③ seed-llm-config.sh 멱등 upsert 계약(SQL 컬럼 집합 + compiled cipher require-path/API) ↔ 실 build/runtime artifact(Prisma LlmProviderConfig 모델 · TS cipher class · tsconfig outDir) parity drift-detection non-gated build-time smoke 신설

## Why

PLAN.md §109(🟢 실 평가 e2e, P5) step③ 및 deployment.md §5.2 의 배포 절차는 `deploy/seed-llm-config.sh` 가 매 재배포 직후(redeploy.sh 31~34행이 호출) **DB 의 `LlmProviderConfig` 행을 멱등 upsert** 해 테스트 기기가 로컬 LLM endpoint(예: 같은 LAN 의 Ollama)를 쓰도록 보장한다(REQ-051 custom provider 슬롯, REQ-061 운영 자동화). 이 seed shell 이 하드코딩한 세 계약은 **실 build/runtime artifact 와 정합해야만 재배포 직후 seed 가 silent 실패 없이 동작하는 운영 contract** 다:

1. **SQL upsert 컬럼 계약**(seed-llm-config.sh 106~113행) — `INSERT INTO "LlmProviderConfig" ("id","provider","endpointUrl","apiKey","modelId","createdAt","updatedAt")` 의 7-컬럼 튜플이 실 Prisma 모델 `LlmProviderConfig` 의 scalar 컬럼 집합과 정합해야 하고, `ON CONFLICT ("id") DO UPDATE SET` 의 5-컬럼 update 집합(`provider`·`endpointUrl`·`apiKey`·`modelId`·`updatedAt`)이 멱등 보존 불변(conflict key `id` 와 `createdAt` 은 update 에서 제외 — 첫 생성 시각 보존)을 지켜야 한다.
2. **compiled cipher require-path 계약**(seed-llm-config.sh 91행) — `require("/app/dist/src/llm/llm-apikey-cipher.service")` 가 app 컨테이너 안 compiled 산출물(`dist/src/llm/llm-apikey-cipher.service.js`)을 가리켜야 한다. 이 경로의 `dist` prefix 는 `tsconfig.json` 의 `outDir: "./dist"` + nest build rootDir 추론(`dist/src/...`, T-0793 이 박제한 동형 emergent 계약)이라는 실 build artifact 에 의존한다.
3. **cipher API 계약**(seed-llm-config.sh 91행) — `new LlmApiKeyCipher().encrypt(d)` 가 실 TS class `LlmApiKeyCipher`(ADR-0014 AES-256-GCM envelope)의 export 명·메서드 시그니처와 정합해야 한다.

만약 누군가 silent 하게 (a) `prisma/schema.prisma` 의 `LlmProviderConfig` 에 NOT NULL scalar 컬럼을 추가하면(seed 의 INSERT 는 그 컬럼을 안 채우고 DEFAULT 도 없어 NOT NULL violation 으로 재배포 직후 seed 실패), (b) 컬럼을 rename 하면(INSERT/ON CONFLICT 가 존재하지 않는 컬럼 타깃 → SQL error), (c) `tsconfig outDir` 를 바꾸면(`/app/dist/src/...` require-path 무효 → cipher 로드 실패), (d) `LlmApiKeyCipher` class/`encrypt` 메서드를 rename·이동하면(require/호출 실패) — 재배포 직후 seed 가 silent crash 하고 평가 orchestrator 가 참조할 `seed-local-llm` config 가 누락돼 실 평가 e2e(step③ Ollama 배선)가 깨진다. 이는 무인 배포·자율 실 평가 e2e(REQ-061·REQ-051)를 무너뜨린다.

직전 sweep 들은 deploy build-time seam 을 차례로 닫았다 — daily-test.sh 의 step_eval jest argv(T-0790)·머신 요약 JSON 스키마(T-0791)·HTTP step 계약↔controller route decorator(T-0792), 그리고 docker-entrypoint.sh 런타임 계약↔build/runtime artifact(T-0793). **T-0792/T-0793 Follow-up (b2) 는 잔여 distinct build-time seam 후보 "`deploy/seed-llm-config.sh` 의 shell↔실 LLM config 스키마/엔드포인트 정합(genuine seam 인지·실 contract 존재 HIGH bar 엄격 재판정 필요; live-LLM gate(PLAN.md 108행 🔴 BLOCKED)와의 경계 주의 — 실 LLM 호출 0·shell 텍스트↔config 스키마 정적 대조만이라야 non-gated)" 를 명시**했다. 본 task 는 그것을 HIGH-bar 로 엄격 재판정해 채택한다 — genuine distinct seam 임을 사전 조사로 확인했고, live-LLM gate 경계를 준수한다(실 LLM 호출·실 docker·실 DB 0, 순수 정적 텍스트 추출만).
