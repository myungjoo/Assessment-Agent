# T-1084 — result-outcome-step-args 구조-검사 선행성 order-lock (variant leg — 기존 spy 블록 재사용)

## Why

P5 test-hardening 의 realdata-e2e 구조-guard 선행성 sweep(T-1065 §D 후보 (a))은 leg 1 result-report-plan(T-1066) → … → leg 17 evaluation-step-args(T-1082) → leg 18 result-publish-step-args(T-1083)로 이어졌다. T-1083 Follow-up 이 leg 19 후보로 **우선 지목**한 **result-outcome-step-args consistency 가드**(`test/helpers/realdata-e2e-result-outcome-step-args-consistency.ts`)를 leg 19 로 삼는다. 이 가드 `assertRealDataResultOutcomeStepArgsConsistentWithSources`(L186~)는 실 평가 e2e build-time chain 의 **step-args layer seam** 산출 `report` 를 single source `(stdout, runPlan.run)` 로 위임 종단 컴포저 `buildRealDataResultIssueOutcomeReportFromOutput(stdout, runPlan.run)`(L201) 재유도해 5 필드(issueNumber/url/gitSha/dateToken/summaryLine) deep-equal 대조하는 seam 무결성 가드다(README.md 109행 step ②→③ 실 평가 e2e build-time chain 의 step-args layer 무결성 / REQ-032·REQ-059). 앞선 result-publish-step-args(T-1083)·evaluation-step-args(T-1082) leg 와 동형이며 재유도 delegate 는 **1개**(`buildRealDataResultIssueOutcomeReportFromOutput`), 구조 assert 는 **2개**(report / runPlan).

**variant 성격(clean-leg 아님)**: T-1082/T-1083 leg 는 spec 이 delegate 를 value import 조차 안 한(type-only) clean gap 이라 **신규 namespace import + spyOn 인프라 신설**이 필요했다. 반면 본 leg 의 spec(총 558줄)은 **이미** delegate `buildRealDataResultIssueOutcomeReportFromOutput` 를 `import * as outcomeReportFromOutputModule`(L24) namespace import 하고, happy-path spyOn 블록(`재유도 위임 호출 검증 — spyOn`, L485~)에서 `jest.spyOn`(L493) + `toHaveBeenCalledTimes(1)`(L502) + `toHaveBeenCalledWith(CREATE_STDOUT, runPlan.run)`(L503) 을 검증하며 `afterEach(() => jest.restoreAllMocks())`(L486) 격리도 갖춰져 있다. 즉 spy 인프라는 이미 존재하고 **결손은 오직 구조 error-path 블록에 delegate `toHaveBeenCalledTimes(0)` 선행성 assert 가 없는 것**이다(pre-check grep: `toHaveBeenCalledTimes(0)` = 0회). 따라서 본 leg 는 **기존 namespace import·spyOn 인프라를 재사용**해 구조 결손 error-path 에 delegate 0-call 만 보강하는 variant 다(신규 namespace import 불요).

planner pre-check(실 grep + read, 2026-07-17, HEAD f3dc6f58 = T-1083 머지 포함)로 확인한 gap: 이 가드는 본문에서 **2 구조 assert**(`assertReportStructure(report)` L194 — report null/undefined·5 필드(issueNumber 비-number·url/gitSha/dateToken/summaryLine 비-string) type 위반 → TypeError; `assertRunPlanStructure(runPlan)` L195 — runPlan null/undefined·`runPlan.run` 비-object → TypeError)를 **outcome-report 재유도 위임**(`buildRealDataResultIssueOutcomeReportFromOutput(stdout, runPlan.run)` L201)보다 **먼저** 수행한다(구조검사 L194~195 < 재유도 L201). result-publish-step-args(T-1083)·evaluation-step-args(T-1082)와 마찬가지로 구조 검사와 재유도 **사이에 RangeError 분기가 없다** — 값 정합 위반 RangeError(필드 drift L209 / L218)는 전부 재유도 **뒤**에 온다. 그러나 대응 spec 의 구조 error-path 블록 2종(`구조 결손 — null/undefined → TypeError` L237~, report null·undefined·runPlan null·undefined·runPlan.run 비-object 3형; `필드 type 위반 → TypeError` L321~, issueNumber 비-number·url·gitSha·dateToken·summaryLine 비-string)은 `.toThrow(TypeError)` / 라벨 regex 만 assert 하고 delegate 호출 횟수를 못박지 않는다. 즉 **구조 결손 입력을 주면 outcome-report 재유도 delegate 가 `toHaveBeenCalledTimes(0)` 이어야 한다는 선행성**이 구조 error-path 에서 spy 로 못박혀 있지 않다. 이를 구조 결손 대표 분기(report null·undefined·issueNumber 비-number·url 비-string·gitSha 비-string·dateToken 비-string·summaryLine 비-string·runPlan null·undefined·runPlan.run 비-object)에 delegate `buildRealDataResultIssueOutcomeReportFromOutput` `toHaveBeenCalledTimes(0)` 으로 못박아 "구조 검사 → 값 재유도" 순서를 silent 재정렬로부터 방어한다(T-1066~T-1083 와 동형 defense-in-depth, delegate 1개). test-only 1파일, production `src`·helper `.ts` 로직 무변경.
