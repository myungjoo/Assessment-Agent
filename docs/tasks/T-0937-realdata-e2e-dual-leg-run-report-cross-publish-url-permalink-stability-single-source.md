# T-0937 — realdata-e2e dual-leg run report cross-publish url permalink stability single-source convergence non-gated smoke

## Why

PLAN.md 109행 (🟢 실 평가 e2e, P5) step④ (daily-test dual-leg run 결과 rolling-issue 멱등 박제) chain 의 **같은 run 을 여러 밤 연속 publish 할 때 사람이 여는 rolling-issue 의 permalink(`outcome.url`)가 어긋나지 않고 안정함** — 즉 1차 create publish 의 `outcome.url` 과 그 이후 모든 update publish 의 `outcome.url` 이 **byte-identical** 하게 같은 `.../issues/M` 을 가리킴 — 이 아직 어떤 smoke 에도 chain 그물로 묶이지 않았다.

REQ-009 멱등("동일 run 의 기존 이슈를 찾아 갱신, 중복 생성 안 함")은 **두 얼굴**을 갖는다:

- **issueNumber 축(republish T-0922 가 봉합)** — 1차 create publish 가 낳은 이슈 번호 M 이 2차 publish 의 marker-search hit 로 다시 관통해 `plan.action.update.issueNumber === M` / `plan.argv[2] === String(M)` 로 좁혀져 2차가 **그 이슈 M 을 정확히 갱신**한다(새 이슈 안 만듦). republish 는 이 **번호 state-transition** 을 자산화한다 — url 은 credential-leak 대조에서만 인용될 뿐 url 안정성은 asserted 축이 아니다.
- **url permalink 축(본 task 가 봉합)** — 사람은 outcome.issueNumber(다음 밤 검색·추적 대상, 내부 식별자)가 아니라 **outcome.url(브라우저로 여는 링크)** 을 실제로 연다. rolling-issue 멱등이 성립하려면 1차 밤에 create 로 받은 permalink `.../issues/M` 이 2차·3차 밤의 update 후에도 **같은 M 을 가리키는 같은 URL** 이어야 한다 — 그래야 사람이 북마크한 링크가 rolling 갱신마다 조용히 다른 이슈로 튀지 않는다. 만약 update output-parse 가 손상 stdout 에서 다른 번호의 url 을 산출하거나, threading 이 어긋나 2차 edit 이 M 아닌 이슈의 permalink 를 돌려주면 — 사람이 여는 링크(outcome.url)가 첫 밤과 다른 이슈를 가리켜 rolling 추적이 사람 눈에는 조용히 끊긴다.

이 **url permalink 가 cross-publish 로 안정함(1차 create url == 2·3차 update url == `.../issues/M`)** 이 REQ-009 멱등의 **사람-링크 무결성** 마지막 그물이다. 그리고 이 안정성의 load-bearing 근거는 literal 하드코딩이 아니라 **1차 create-output 이 낳은 M 이 2차·3차 edit execStdout 의 permalink 로 다시 관통** 함이다: 2차 edit execStdout 을 `.../issues/${outcome1.issueNumber}` 로 구성(M 을 1차 outcome 에서 threading, republish 가 봉합한 그 threaded M) → output-parse → `outcome2.url === outcome1.url`.

그러나 이 **cross-publish url permalink stability single-source** 를 어느 smoke 도 검증하지 않는다:

- 형제 republish(T-0922, create-update idempotency)는 1차 create-output 의 M 이 2차 search-input 으로 threading 해 2차 resolve 가 `update`/M 으로 좁혀짐(**issueNumber state-transition**)만 자산화한다 — url 은 두 cycle 어디에서도 credential/raw 누출 0 대조(leak-check)에서만 등장하고, **두 publish 의 outcome.url 이 서로 byte-identical(permalink 안정)** 함은 미단언(번호 축 ≠ 사람-링크 축).
- 형제 T-0936(output-parse url↔issueNumber cross-field)은 **단일 outcome 내부**에서 url 이 그 outcome 의 issueNumber 를 포함(url ⊇ issueNumber, `.../issues/${issueNumber}`)함만 자산화한다 — **여러 publish 에 걸친 url 의 동일성(cross-publish 안정)** 은 대상이 아니다(intra-outcome ≠ cross-publish).
- 형제 T-0924(output-stdout-value-consistency)는 outcome 전체 값(url 포함)이 **자기 raw stdout 으로부터 독립 재유도한 expected 와 deep-equal** 임만 자산화한다 — 각 publish 의 outcome 을 **자기 stdout 과 개별** 대조할 뿐, **여러 publish 의 url 상호 동일성**은 못 박지 않는다.
- 형제 T-0935(create genesis)·T-0920(update convergence)은 issueNumber 의 출처/관통만, T-0923(parse-shape)은 outcome key set 만 자산화한다 — url permalink 의 cross-publish 안정성과 무관.

본 task 는 그 **cross-publish url permalink stability seam** 을 닫는다 — republish(T-0922)의 issueNumber-M threading 의 **url 짝**. chain: 두 leg outcome + run → report → descriptor → commandArgs 를 통과시켜 유효 commandArgs 를 얻고, (1차) 빈 search(`"[]"`)로 create plan → create execStdout(`.../issues/M`) → output-parse → outcome1, (2차/3차) **outcome1.issueNumber(=M) 를 담은** marker-매칭 hit → update plan(`plan.argv[2]===String(M)`) → edit execStdout(`.../issues/${outcome1.issueNumber}`) → output-parse → outcome2/outcome3 를 산출한 뒤 `outcome2.url === outcome1.url` AND `outcome3.url === outcome1.url`(byte-identical, 모두 `.../issues/M`)임을 박제한다.

issue-still-relevant 확인(2026-07-12): `ls test/smoke | grep dual-leg | grep -iE "cross-publish|permalink|url.*stab|stab.*url"` = **0개**(cross-publish url permalink stability seam 미봉합). republish smoke(T-0922) 안 `url`/`permalink` 어휘는 credential-leak `not.toContain` 대조에만 등장(url 동일성 단언 0). `git log origin/main` 동일 영역(dual-leg cross-publish url permalink smoke) 박제 commit 0. output-parse 파서(`parseRealDataDailyStepDualLegRunReportIssueCreateEditOutput`, T-0903)·종단 컴포저(T-0902)·argv 빌더(T-0899) 배선은 이미 main 에 박제됨 — 본 task 는 그 배선을 **다시 만들지 않고** 여러 publish 의 outcome.url 상호 동일성을 대조하는 **smoke 그물만** 신설.
