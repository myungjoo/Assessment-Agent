# T-0783 — realdata-e2e step④ aggregator collect-call-args 합류 14-way single-source closure non-gated build-time smoke 신설

## Why

PLAN.md §109(🟢 실 평가 e2e, P5)의 build-time 순수 layer 는 최외곽 단일 진입 `buildRealDataE2eRunPlan(seeds, modelId, run)` → `{pipeline, run}`(T-0597)을 산출하고, 그 검증된 `runPlan` 을 pre-실행 aggregator `buildRealDataE2eStepArgs(runPlan, activities, results)` → `{evaluation, publish}`(T-0601)에 통째로 넘긴다. 직전 sweep(T-0778~0782)은 aggregator 산출의 **evaluation-leg(inputs·callArgs·modelId)** 와 **publish-leg(report·commandArgs·searchArgv·resolve-argv)** 두 leg 의 전 표면을 단일 source 로 묶어 13-way 를 완성했다.

그러나 `runPlan` 에는 세 번째 leg 가 있다 — **collect-leg(`runPlan.pipeline.collectCallArgs`)**. 이는 step② 실 수집 runner 가 받을 `collectForPerson(person, since, assessmentId)` 호출-args 묶음(seed-side 진입 plan, `buildRealDataPipelinePlan(seeds, modelId)` → `{collectCallArgs, modelId}`, T-0592 산출)이다. aggregator `buildRealDataE2eStepArgs` 는 그 `runPlan` 을 evaluate/publish 두 leg 로만 thread 하고 **collect-leg 를 산출 표면으로 surface 하지 않는다** — collect-leg 는 `runPlan.pipeline` 으로 aggregator 옆을 흐르되 같은 검증 source 임이 convergence closure 에 미합류된 distinct 표면이다.

collect-leg(collectCallArgs) 축은 evaluation-leg/publish-leg(T-0782) 와 distinct 한 표면이다:

- **collect-leg call-args 재유도 축(본 task 의 새 표면)** — `runPlan.pipeline.collectCallArgs: RealDataCollectCallArgs[]` 는 `buildRealDataCollectCallArgs(seeds)`(`realdata-e2e-seed-collect-call-args.ts`, T-0577)가 산출한 묶음이다:
  - 각 원소 `{person: CollectForPersonInput, since: undefined, assessmentId: ASSESSMENT_ID_PLACEHOLDER}`(call-args 58~62·85~91행). `since` 는 신규 seed 인원이라 결정론 상수 `undefined`(full collection), `assessmentId` 는 결정론 상수 `ASSESSMENT_ID_PLACEHOLDER`, `person` 은 seed descriptor 1:1 매핑.
  - 이 collect-leg 는 aggregator 가 evaluate/publish 로 thread 하는 **그 동일 `runPlan` 의 pipeline** 에서 나온다. 즉 `runPlan.pipeline.collectCallArgs == buildRealDataCollectCallArgs(seeds)`(byte-identical 재유도) AND collect-leg 의 modelId(`runPlan.pipeline.modelId`)가 evaluation-leg 의 `callArgs[].options.modelId` 로 동형 thread 됨이 collect→evaluate→publish→resolve→post 종단 closure 에 미합류.

직전 sibling 들은 이 collect-leg 축을 aggregator convergence closure 에 합류시키지 않았다:
- **T-0782 (aggregator 13-way)**: search-argv 전체-벡터 위치-정합 + resolve-argv + command-args + descriptor + summary + inputs + modelId + marker + resolve + post 를 묶었으나, 그 modelId 는 publish/evaluate leg 의 `runPlan.pipeline.modelId` thread 만 확인 — **collect-leg(`collectCallArgs`) 자체의 재유도·collect-leg 가 같은 runPlan 의 collect 산물임은 미합류**.
- **T-0775~0778 (aggregator 4~11-way)**: 전부 evaluation/publish 두 leg 산출만 convergence 축으로 잡음. 11-way 에 `collectCallArgs` 가 1회 등장하나 그것은 synthetic runPlan 합성용 incidental 일 뿐 — `buildRealDataCollectCallArgs(seeds)` 와의 재유도 `toEqual`·collect-leg modelId thread 단언 0.
- **collect-leg self-guard**: `assertRealDataCollectCallArgsConsistentWithSources`(T-0688, call-args 101행) + `assertRealDataPipelinePlanConsistentWithSources`(T-0680) 가 빌더 내부 self-wire 로 round-trip 을 박제했으나 **aggregator(`buildRealDataE2eStepArgs`) 진입·evaluate/publish thread·resolve·post 미합류**(빌더 단독 self-guard).
- **pipeline-plan / run-plan dual-leg smoke**(`realdata-e2e-pipeline-plan-dual-leg-convergence`·`realdata-e2e-run-plan-dual-leg-convergence`): `buildRealDataPipelinePlan`/`buildRealDataE2eRunPlan` 단독에서 collectCallArgs↔modelId 두 leg 를 묶었으나 **aggregator(step-args) → evaluate/publish/resolve/post 종단 chain 미합류**(run-plan 단독 dual-leg).

본 task 는 그 빈 자리를 채워 **collect-leg(seed-side 수집 호출-args 묶음)가 같은 검증 source `(seeds, modelId, run)` 에서 나온 `runPlan` 의 pipeline 임을, aggregator 가 그 동일 runPlan 으로 thread 한 evaluation-leg modelId·publish-leg·resolve·post 와 묶어 closure 에 합류**시킨다. 단일 source `(seeds, modelId, run, activities, results, search-stdout, exec-stdout)` 로부터:

1. **collect-leg call-args 재유도(축 14, 본 task 의 새 표면)** — `runPlan = buildRealDataE2eRunPlan(seeds, modelId, run)` → `runPlan.pipeline.collectCallArgs` 가 **byte-identical deep-equal**(`toEqual`) `buildRealDataCollectCallArgs(seeds)`. 각 원소의 `since === undefined`(결정론 상수)·`assessmentId === ASSESSMENT_ID_PLACEHOLDER`(결정론 상수)·`person` 이 seed 1:1 매핑임 확인. collectCallArgs 길이 == seeds 길이.
2. **collect-leg → evaluation-leg modelId thread(축 14 묶음 — 두 leg 동일 source)** — `runPlan.pipeline.modelId === modelId`(입력 정책) AND `stepArgs.evaluation.callArgs[i].options.modelId === runPlan.pipeline.modelId`(aggregator 가 collect-leg 와 같은 pipeline.modelId 를 evaluation 으로 thread). 즉 collect-leg 와 evaluate-leg 가 같은 단일 modelId source 를 공유.
3. **search-argv 전체-벡터 위치-정합(축 13, 13-way 묶음 항)** — `stepArgs.publish.searchArgv` 가 byte-identical deep-equal `["search","issues","--match","body",commandArgs.searchQuery,"--json","number,title,body","--limit","30"]`, `searchArgv[4]===commandArgs.searchQuery`.
4. **resolve-argv update/create 위치-정합(축 12, 묶음 항)** — search hit N → `resolvePlan.argv == ["issue","edit",String(N),"--title",updateArgs.title,"--body",updateArgs.body]`, hit 0 → `["issue","create","--title",createArgs.title,"--body",createArgs.body,"--label","realdata-e2e","--label","result"]`.
5. **publish-leg command-args-labels 고정상수 + title/body 두 경로(축 9~11)** — `createArgs.labels` deep-equal `["realdata-e2e","result"]`, `createArgs/updateArgs.{title,body}` 가 `descriptor.{title,body}` 와 byte-identical.
6. **publish-leg descriptor-{title,body}·summary 재유도(축 6~8)** — `descriptor.{title,body}`·`report.summary` 가 `buildRealDataResultIssueCommandPlan(results, runPlan.run).report.{...}` 와 byte-identical.
7. **evaluation-leg inputs 재유도 + 페어링 + modelId(축 4~5)** — `evaluation.inputs == buildRealDataEvaluationInputs(activities)`, `callArgs[i].input === inputs[i]`, `callArgs[i].options.modelId === runPlan.pipeline.modelId`.
8. **publish-leg marker 3-축(축 2~3)** — `descriptor.marker === commandArgs.searchQuery === searchArgv[4]`.
9. **resolve issueNumber + post run-identity(축 1, 종단)** — `resolvePlan.action.update.issueNumber = N` → `outcomeReport = buildRealDataResultOutcomeStepArgs(runPlan, execStdout)` → `{issueNumber, gitSha, dateToken, ...}` 가 동일 runPlan.run 전파.

이 14-way(collect-leg call-args 재유도 + collect/evaluate modelId 공유 thread + search-argv 전체-벡터 위치-정합 + resolve-argv 위치-정합 + command-args labels 고정상수 + command-args title/body 두 경로 + descriptor.{title,body} 재유도 + summary + inputs + marker 3-축 + resolve issueNumber + post run-identity)가 **검증 source `(seeds, modelId, run, activities, results)`** single-source 로 수렴함이 **search-or-update 멱등성**(REQ-009)·**raw 미보유 평가 입력/결과 집계 정합**(REQ-032)·**결과 리포트 재실행 정합**(REQ-037)의 aggregator-level "step② collect 호출-args(seed-side)·step③ evaluate(modelId)·step④ publish/resolve/post 세 leg 가 모두 같은 단일 검증 source 의 산물" 의 종단 닫음이다. **e2e 의 세 단계 leg(collect·evaluate·publish) 가 단일 검증 runPlan source 에서 동시 thread 되는 slice** 다.

gap 확인(git grep, origin/main 62a4de1f): aggregator-* sweep smoke 13파일(4~13-way) 중 collect-leg(`collectCallArgs`) convergence 축 합류 0(11-way 에 `collectCallArgs` 1회 등장은 synthetic runPlan 합성용 incidental — `buildRealDataCollectCallArgs(seeds)` 재유도 `toEqual` 0). `aggregator-*collect-call-args* smoke 파일 부재` + `git log origin/main` 동일 영역 박제 commit 0. (pipeline-plan-dual-leg·run-plan-dual-leg smoke 는 run-plan 단독에서 collect↔modelId 두 leg 를 묶으나 aggregator → evaluate/publish/resolve/post 종단 chain 미합류.)

live leg(실 prisma·실 collectForPerson·실 github.com fetch·실 LLM scoring·실 gh CLI 실행·DB·LAN gate) 복제 0·non-gated 항상 실행 — 순수 build-time in-memory 검증만.
