# T-1083 — result-publish-step-args 구조-검사 선행성 order-lock

## Why

P5 test-hardening 의 realdata-e2e 구조-guard 선행성 sweep(T-1065 §D 후보 (a))은 leg 1 result-report-plan(T-1066) → … → leg 16 seed-collect-call-args(T-1081) → leg 17 evaluation-step-args(T-1082)로 이어졌다. T-1082 Follow-up 이 적격 후보(step-args family)로 지목한 잔여 가드 중 **result-publish-step-args consistency 가드**를 leg 18 로 삼는다. 이 가드 `assertRealDataResultPublishStepArgsConsistentWithSources`(`test/helpers/realdata-e2e-result-publish-step-args-consistency.ts`)는 실 평가 e2e build-time chain 의 **step-args layer seam** `buildRealDataResultPublishStepArgs(runPlan, results)` 산출 publish plan `{ report, commandArgs, searchArgv }` 을 single source `(results, runPlan.run)` 로 위임 종단 컴포저 `buildRealDataResultIssuePublishPlan(results, runPlan.run)` 재유도해 deep-equal 대조하는 seam 무결성 가드다(README.md 109행 step ②→③ 실 평가 e2e build-time chain 의 step-args layer 무결성 / REQ-032·REQ-059). 앞선 seed-collect-call-args(T-1081)·evaluation-step-args(T-1082) leg 와 동형이며 재유도 delegate 는 **1개**(`buildRealDataResultIssuePublishPlan`), 구조 assert 는 **2개**(plan / runPlan — evaluation-step-args T-1082 의 3개 vs seed-collect T-1081 의 2개 중 후자와 동수).

**후보 선택 근거(pre-check 반영)**: T-1082 Follow-up 은 result-outcome-step-args 를 leg 18 로 우선 지목했으나, 본 planner pre-check(실 grep + read, 2026-07-17, HEAD 3bd8c18c) 결과 `realdata-e2e-result-outcome-step-args-consistency.spec.ts` 는 **이미** delegate `buildRealDataResultIssueOutcomeReportFromOutput` 를 namespace import(L24) 하고 happy-path 블록(L485~)에서 `jest.spyOn` + `toHaveBeenCalledTimes(1)` + `toHaveBeenCalledWith` 를 검증 중이다(spyOn 3 / toHaveBeenCalled 2). 즉 delegate 가 이미 spy 대상이라 '엄격 spyOn 0' 기준을 만족하지 못한다(구조 결손 0-call gap 은 남지만 clean leg 아님). 반면 result-publish-step-args-consistency.spec 은 spyOn 0 / toHaveBeenCalled 0 / delegate value import 부재로 sweep 의 exact-match gap 이라 leg 18 로 우선한다(result-outcome 은 별도 후속 leg 에서 기존 spy 블록에 구조 결손 0-call 만 보강).

planner pre-check(실 grep + read, 2026-07-17, HEAD 3bd8c18c = T-1082 머지 포함)로 확인한 gap: 이 가드는 본문에서 **2 구조 assert**(`assertPlanStructure(plan)` L197 — plan null/undefined·`plan.report` 비-object·`plan.commandArgs` 비-object·`plan.searchArgv` 비-배열·searchArgv 원소 비-string → TypeError; `assertRunPlanStructure(runPlan)` L198 — runPlan null/undefined·`runPlan.run` 비-object → TypeError)를 **publish-plan 재유도 위임**(`buildRealDataResultIssuePublishPlan(results, runPlan.run)` L204)보다 **먼저** 수행한다(구조검사 L197~198 < 재유도 L204). seed-collect-call-args(T-1081)·evaluation-step-args(T-1082)와 마찬가지로 구조 검사와 재유도 **사이에 RangeError 분기가 없다** — 값 정합 위반 RangeError(report drift L208 / commandArgs drift L215 / searchArgv drift L222)는 전부 재유도 **뒤**에 온다. 그러나 대응 spec(총 475 line)은 delegate `buildRealDataResultIssuePublishPlan` 를 **value 로 import 하지 않으며**(L23 은 `RealDataResultIssuePublishPlan` type-only import) `spyOn`·`toHaveBeenCalled`·`toHaveBeenCalledTimes(0)`·`invocationCallOrder` 가 **0회** 다 — 구조 error-path 블록(L270 `구조 결손 — null/undefined → TypeError`, L326 `구성요소 type 위반 → TypeError`)은 `.toThrow(TypeError)` / 라벨 regex 만 assert 하고 delegate 호출 횟수를 못박지 않는다. 즉 **구조 결손 입력을 주면 publish-plan 재유도 delegate 가 `toHaveBeenCalledTimes(0)` 이어야 한다는 선행성**이 spy 로 못박혀 있지 않다. 이를 구조 결손 대표 분기(plan null·undefined·비-object·report 비-object·commandArgs 비-object·searchArgv 비-배열·searchArgv 원소 비-string·runPlan null·undefined·runPlan.run 비-object)에 delegate `buildRealDataResultIssuePublishPlan` `toHaveBeenCalledTimes(0)` 으로 못박아 "구조 검사 → 값 재유도" 순서를 silent 재정렬(예: 리팩터가 재유도를 구조 검사 위로 끌어올림)로부터 방어한다(T-1066~T-1082 와 동형 defense-in-depth, delegate 1개). test-only 1파일, production `src`·helper `.ts` 로직 무변경.
